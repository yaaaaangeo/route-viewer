# Route Viewer (경로 뷰어) v3.1.2

nav-app 주행기록(.xlsx/.csv)을 **로컬 데이터베이스에 계속 쌓아두고** 달력 · 누적 지도 ·
Coverage · 통계 · GPS 리플레이로 보는 데이터 관리/분석 도구입니다.

- 버전: `package.json` 기준 **3.1.2** (화면 좌측 하단 배지 `APP_VERSION`도 v3.1.2)
- 저장소: 데스크톱 앱 = **SQLite**, 브라우저로 열면 = **IndexedDB** (화면 코드는 같은 `RouteDB` 인터페이스만 씀)

---

## 주요 기능

- **파일 불러오기는 "추가(merge)"** — 새 파일을 넣어도 기존 날짜 기록은 지워지지 않습니다.
  중복 판정 키는 `date | time | vehicle | lat(소수점 6자리) | lng(소수점 6자리)`이고,
  같은 키인데 `place/road/weather/timeOfDay/traffic/speed` 값이 다르면 "충돌"로 따로 집계합니다.
- **Import History** — 파일별 원본/추가/중복/충돌 건수, 대표 차량·거리, 불러온 사람, 충돌 상세.
- **Import 이슈 기록 · 이슈 데이터 분리** — 파일을 저장하기 전에 "이 파일에 이슈가 있나요?"를 파일별로 묻고,
  이슈로 표시한 파일에서 온 GPS 기록을 달력·누적 지도·Coverage·통계·추천에서 **데이터 상태 필터**
  (전체 / 이슈 없음 / 이슈만)로 함께 걸러 볼 수 있습니다. 누적 지도의 이슈 칸과 통계 막대의 이슈 몫은
  **회색**으로 그려서 한눈에 구분됩니다.
- **전체 데이터 수집 현황** — 달력 맨 위 표에 KPI·제안 목표 대비 누적 주행 시간·수집 시간과 진행률.
- **달력 · 일자 요약** — 달력 칸마다 그 날의 수집·주행 시간, 날짜를 열면 운행 시간·구역·차량·주행 거리·기록 수·
  주행 시간(첫~마지막 기록)·수집 시간(GPS 실제 기록)·GPS 공백/점프, **교통 시간대 · 조도 조건 분포(분 · 기록 수)와
  조건 조합**.
- **교통 시간대 · 조도 조건** — 한 기록이 교통 시간대(출근·점심·퇴근 등)와 조도 조건(주간·일출·일몰·야간)을 따로
  동시에 가집니다. 요일(평일/주말)·날씨와 함께 `평일 · 퇴근 피크 · 일몰 전후 · 비` 같은 복합 조건으로 집계합니다.
- **누적 지도** — 전체 또는 선택한 날짜 범위 기록의 밀도 지도 + 구역별 **Coverage Map**,
  현재 지도 **PNG 캡처**(데스크톱 앱·브라우저 모드).
- **통계** — 지역별/차량별 분포, 교통 시간대·조도 조건·평일/주말별 수집 시간과 기록 수, 구역·차량별 시간대 표.
- **추천 주행** — 부족한 구역·요일·교통 시간대·조도·날씨 조합을 통계로 찾아 점수·근거·권장 시간·추가 횟수까지 제시합니다
  (예상 Edge Case 는 가능성 추정, LLM 미연결).
- **주행 계획** — "오늘 8시부터 나가면?" 처럼 **운행 시간을 바꿔 보고** 그 시간에 어디부터 어떻게 돌지를
  시각 블록으로 받아봅니다. 지금 운행 시간(기본 09:00~18:00)과 비교해서 무엇이 새로 잡히는지도 함께 보여줍니다.
- **설정** — 차량/지역 추가·비활성화(삭제 아님), Coverage Depth 등급 기준, 교통 시간대 시각, 일출·일몰 전후 범위.
- **데이터 관리** — 날짜별/전체 삭제(삭제는 여기서만), 서버 동기화 설정.
- **백업/복구** — 병합 복구(기본) / 전체 교체 복구(주행 기록만 교체, 설정·수동 셀은 지우지 않음).

## 달력 — 전체 데이터 수집 현황

달력 탭 맨 위에 DB에 저장된 **전체 기간** 데이터의 누적 현황을 표로 보여줍니다(보고 있는 달·선택한 날짜와 무관).

| 구분 | 목표 Clip 수 | 목표 시간(분) | 주행 시간(분) | 수집 시간(분) | 진행률(%) |
|---|---:|---:|---:|---:|---:|
| KPI | 8,000 | 4,000 | 자동 계산 | 자동 계산 | 수집 시간 ÷ 4,000 × 100 |
| 제안 | 20,000 | 10,000 | 자동 계산 | 자동 계산 | 수집 시간 ÷ 10,000 × 100 |

- **두 가지 시간을 따로 보여줍니다.**
  - **주행 시간** — 날짜·차량별 첫 기록부터 마지막 기록까지(점심·휴식 등 GPS가 끊긴 시간 포함). "마지막 시각 − 첫 시각"
    단순 계산과 같은 값입니다(`CollectionStats.spanDurationSec`).
  - **수집 시간** — 그중 GPS가 실제로 기록된 시간(아래 규칙). **진행률은 수집 시간 기준**이며, 진행률 아래에 주행 시간
    기준 진행률을 참고로 작게 적습니다(예: "주행 기준 142.7%").

- **목표값**은 `src/js/collection-stats.js`의 `COLLECTION_TARGETS` 한 곳에서 관리합니다(표의 행도 이 목록으로 그림).
  목표 Clip 수는 현재 목표값만 표시하고, 진행률은 **수집 시간 기준**입니다.
- **수집 시간(유효 수집 시간)** 계산 규칙 — SQLite와 IndexedDB가 같은 함수(`CollectionStats.validDurationSec`)를 씁니다.
  1. 날짜별 · 차량별로 기록을 나눕니다.
  2. 차량마다 시각 순으로 정렬하고(같은 시각 기록은 하나로 봄) 연속한 두 기록의 간격을 구합니다.
  3. 간격이 0초 초과 **90초 이하**면 더하고, **90초보다 긴 간격은 GPS 공백으로 보고 뺍니다**
     (기존 품질 검사의 "GPS 공백" 기준과 같은 값). 오전 1시간 + 오후 1시간 = 2시간(마지막−처음 = 9시간이 아님).
  4. 차량별 합계를 더합니다 — 여러 차량이 같은 시간대에 수집하면 각각 따로 셉니다.
  5. 모든 날짜를 더해 초 → 분으로 바꿉니다. 표의 수집 시간은 반올림한 정수 분, 진행률은 초 단위 값으로 계산해
     소수 첫째 자리까지 표시합니다(예: 1,234분 → KPI 30.9%, 제안 12.3%).
- **중복 제외**: import 때 `date|time|vehicle|lat|lng`로 중복 제거돼 DB에 실제로 남은 기록만 씁니다. 같은 파일 재등록,
  동일 GPS 레코드, 삭제된 날짜는 들어가지 않고, 같은 차량·같은 시간대의 겹친 세션은 시각을 합쳐서 한 번만 셉니다.
  (차량 이름이 파일마다 다르게 적혀 있으면 — 예: "토레스 3호"/"토레스 3호차" — 다른 차량으로 셉니다.)
- **목표 초과**: 진행률 숫자는 100%로 자르지 않고 그대로(예: 4,500분 → 112.5%), 진행 막대 너비만 최대 100%입니다.
  데이터가 없으면 수집 시간 `0`, 진행률 `0.0%`입니다. 표 오른쪽 위에 DB의 가장 최신 기록 날짜를 "최근 데이터"로 표시합니다.
- **저장·성능**: 날짜별 유효 수집 시간은 import·삭제·백업 복원·서버 동기화 때 만들어지는 날짜 요약에
  `collectionSec`(수집)·`driveSpanSec`(주행)로 저장되고, 달력은 날짜 요약만 더합니다(원본 GPS 기록을 다시 읽지 않음).
  이 값이 없는 예전 DB는 앱을 처음 켤 때 날짜 요약을 한 번 다시 만듭니다(`summary_version` 4 — 4에서 교통 시간대·조도
  조건 칸이 추가됨, 아래 "교통 시간대 · 조도 조건" 참고).
- **자동 갱신**: 앱 시작, 파일 import, 날짜/전체 삭제, 백업 복원, 서버 동기화 뒤 날짜 요약을 다시 읽을 때
  (`refreshDateIndex`) 한 번만 다시 합산합니다. 월 이동·날짜 선택으로는 다시 계산하지 않습니다.
- **달력 칸**마다 그 날짜의 `수집 N분 · 주행 N분`을, **일자 요약**(날짜 클릭)에는 주행 시간과 수집 시간을 따로
  보여줍니다(수집 시간 옆에 "공백 N분 제외").
- 참고: 이 저장소의 `주행기록/` 28개 파일(14일)을 넣으면 **주행 5,706분 · 수집 3,093분**입니다
  (진행률 KPI 77.3%·제안 30.9%, 주행 기준 참고값 KPI 142.7%·제안 57.1%). 빠진 2,613분의 대부분은 하루 1~3시간씩
  기록이 통째로 없는 구간입니다 — 30분 넘는 공백 28개가 1,919분, 10~30분 공백 25개가 478분, 90초~10분 공백은
  216분뿐입니다(주행 중 기록 간격은 대부분 10초 이하).

## 교통 시간대 · 조도 조건

### 왜 두 축으로 나눴나

예전에는 "시간대"가 파일의 `시간대` 열(nav-app이 넣은 `주간`/`일몰`) 하나뿐이었습니다. 여기에 출근·퇴근 같은 피크타임을
섞으면 `퇴근 일몰` 같은 값이 생겨 "퇴근 피크인데 아직 밝은 날"과 "퇴근 피크이면서 해가 지는 날"을 구분할 수 없습니다.
교통 흐름과 빛의 상태는 서로 독립이라 **서로 다른 필드**로 둡니다.

| 축 | 필드 | 기준 | 값(내부 식별자 → 화면) |
|---|---|---|---|
| 교통 시간대 | `trafficPeriod` | 고정 시각 구간(설정에서 수정) | `late_night` 심야 · `early_morning` 이른 아침 · `morning_peak` 출근 피크 · `morning_offpeak` 오전 비피크 · `lunch_peak` 점심 피크 · `afternoon_offpeak` 오후 비피크 · `evening_peak` 퇴근 피크 · `night` 야간 · `unknown` 미분류 |
| 조도 조건 | `lightCondition` | 날짜·GPS로 계산한 일출·일몰 | `sunrise` 일출 전후 · `daylight` 주간 · `sunset` 일몰 전후 · `night` 야간 · `unknown` 미분류 |
| 요일 | `weekdayType` | 날짜 | `weekday` 평일 · `weekend` 주말 · `unknown` 미분류 |
| 날씨 | `weather` | 파일 `날씨` 열 원본 | 원본 문자열 그대로(`맑음`/`흐림`/`비`, 없으면 빈 값 = "정보 없음") |

- 저장·비교는 항상 **내부 식별자**로 하고 화면 이름은 `src/js/time-conditions.js`의 라벨 표에서만 붙입니다 — 이름을 바꿔도
  기존 데이터가 깨지지 않습니다.
- 교통 시간대의 `야간`(20:00~24:00 고정 구간)과 조도 조건의 `야간`(해가 없는 시간)은 이름만 같고 다른 값입니다
  (예: 6월 21일 20:05 → 교통 `야간` + 조도 `일몰 전후`). 하나의 변수·컬럼으로 합치지 않습니다.
- 파일의 `시간대` 열(`timeOfDay`)은 **삭제하거나 의미를 바꾸지 않고** 원본 그대로 보존합니다. 통계 탭에는
  "파일 원본 시간대" 카드로 남아 있습니다. 참고로 이 저장소의 실제 기록에서 원본 `일몰`(17시대 4,763건)은 실제 일몰
  (18:40~19:28)보다 1시간 이상 일러서 계산된 조도 조건은 `주간`입니다 — 두 값이 다른 게 정상입니다.

### 교통 시간대 — 기본값과 경계 규칙

| 교통 시간대 | 시작 | 종료 |
|---|---:|---:|
| 심야 | 00:00 | 05:00 |
| 이른 아침 | 05:00 | 07:00 |
| 출근 피크 | 07:00 | 10:00 |
| 오전 비피크 | 10:00 | 11:30 |
| 점심 피크 | 11:30 | 13:30 |
| 오후 비피크 | 13:30 | 17:00 |
| 퇴근 피크 | 17:00 | 20:00 |
| 야간 | 20:00 | 24:00 |

- **`시작 <= 시각 < 종료`** — 초 단위까지 봅니다(`04:59:59` 심야, `05:00:00` 이른 아침, `23:59:59` 야간).
- `24:00`은 다음 날 `00:00`과 같은 경계입니다. 설정의 종료 `00:00`은 `24:00`으로 저장되고, 기록 시각 `24:00:00`은 심야입니다.
- 종료를 시작보다 이르게 쓰면 자정을 넘는 구간입니다(예: 심야 `22:00~05:00`).
- 시각이 없거나 파싱할 수 없는 기록(`25:00:00`, 문자 등)은 임의의 구간에 넣지 않고 `unknown`(미분류)입니다.
- 판정은 이름·배열 순서가 아니라 **저장된 시작·종료 시각**으로만 합니다.

### 설정 탭에서 수정하기

[설정] → **교통 시간대**에서 각 구간의 시작·종료를 `HH:mm`으로 고치고 **저장**, 기본값으로 돌리려면 **기본값 복원**
(바로 저장·재분류). 입력하는 동안 검증 결과를 보여주고, 아래 중 하나라도 있으면 저장 버튼이 꺼지고 이유가 표시됩니다.

- 형식 오류(`7:00`, `07:60`, 시작 `24:00`) · 시작=종료(길이 0) · 빠진/중복/알 수 없는 시간대
- **겹침** — 예: `출근 피크(07:00~10:00)와(과) 오전 비피크(09:30~11:30)이(가) 09:30~10:00에서 겹쳐요.`
- **공백** — 예: `11:00~11:30이(가) 어느 교통 시간대에도 속하지 않아요(공백).`
- 하루 1,440분이 정확히 한 번씩 덮이는지 분 단위로 확인합니다.

같은 검증(`TimeConditions.validateTrafficPeriods`)을 저장소(SQLite `setSettings` / IndexedDB `setSettings`)가 저장 직전에
다시 하므로 화면을 거치지 않은 잘못된 설정도 저장되지 않습니다. 설정 구조(`app_settings`, 두 저장소 동일):

```js
trafficPeriods: [{ id: 'late_night', label: '심야', start: '00:00', end: '05:00' }, …],  // 시작 시각 순으로 저장
sunriseWindowMinutes: 30,
sunsetWindowMinutes: 30,
```

저장값이 없거나(구버전) 깨졌으면 기본값으로 판정합니다. 백업·서버 동기화로 들어온 잘못된 분류 설정은 그 값만 무시하고
지금 설정을 유지합니다.

### 조도 조건 — 일출·일몰 계산

- **계산 방식**: 외부 API 없이 로컬 계산 — NOAA Solar Calculator와 같은 Meeus 천문 알고리즘(태양 적위·균시차를 일출·일몰
  시각에서 반복 보정, 천정각 90.833° = 대기 굴절·태양 반지름 반영). 입력은 **주행 날짜 · GPS 위도 · GPS 경도 · 시간대**.
- **정확도**: 미 해군천문대(USNO) 공개값과 강남(37.4979, 127.0276) 기준 2026년 춘분·하지·8/12·9/15·동지 모두 **1분 이내**
  (실측 오차 최대 0.5분, `tests/time-conditions-test.js`에 기준값·출처 URL 포함).
- **캐시**: `날짜 + 위도·경도(0.01° ≈ 1.1km 반올림)`로 계산 결과를 재사용합니다. 반올림한 좌표로 계산하므로 캐시와
  무관하게 항상 같은 값입니다. 실제 기록 약 20만 번 조회에 계산 335번이었습니다.
- **범위(기본 ±30분, 경계 포함)**: 일출 ± `sunriseWindowMinutes` → 일출 전후 · 일몰 ± `sunsetWindowMinutes` → 일몰 전후 ·
  그 사이 → 주간 · 나머지 → 야간. 겹치면 일출 전후가 우선입니다. [설정] → **조도 조건**에서 0~180분으로 바꿀 수 있습니다.
- 백야/극야(일출·일몰이 없는 날)는 각각 주간/야간입니다.
- **날짜 없음**(`날짜미상`, 없는 날짜) · **GPS 없음**(빈 값·NaN·범위 밖·`0,0`) · 시각 파싱 실패 → `unknown`(미분류).
  날짜만 없으면 교통 시간대는 시각으로 정해지고 조도·요일만 미분류입니다.

### 한국 현지 시간 처리

- 기록의 `date`(`YYYY-MM-DD`)·`time`(`HH:MM:SS`)은 이미 한국 현지 벽시계 값입니다. 분류 코드는 `new Date('…T…')`처럼
  실행 환경 시간대로 해석되는 변환을 쓰지 않고 문자열을 숫자로 쪼개 계산합니다(`Date` 객체 입력은 받지 않음).
- 일출·일몰은 UTC로 계산한 뒤 **고정 오프셋 `Asia/Seoul` = +09:00**(서머타임 없음)을 더합니다.
- 테스트가 같은 계산을 `TZ=UTC` · `TZ=America/Los_Angeles` · `TZ=Asia/Seoul` 자식 프로세스로 돌려 66건 결과가 모두
  같은지 확인합니다(각 프로세스의 실제 시간대 오프셋 0/420/-540도 확인).

### 저장 방식 · 재분류

**선택: 파생값은 기록에 저장하지 않고, 날짜 요약에만 "조건 칸 + 분류 서명"으로 캐시한다.**

- 교통 시간대·조도·요일은 원본(시각·날짜·GPS)에서 다시 계산할 수 있는 파생값입니다. `driving_records`(SQLite)·
  `records`(IndexedDB)에는 컬럼/필드를 추가하지 않았고, 기록을 읽을 때(`getRecordsByDate`) 지금 설정으로 계산해 붙입니다.
- 날짜 요약(`date_summaries.summary_json` / `summaries`)에 **조건 칸 `conditionCells`**를 저장합니다 — 칸 하나 =
  `zone × vehicle × weekdayType × trafficPeriod × lightCondition × weather` 조합이고, 칸마다 `recordCount` ·
  `collectionSec`(유효 수집 시간) · `firstTime` · `lastTime`을 가집니다(실제 기록 기준 날짜당 수십 칸).
- 요약마다 **`classificationSignature`**(판정 규칙 버전 `CLASSIFICATION_VERSION` + 교통 시간대 + 일출·일몰 범위 + 시간대)를
  같이 적습니다. 서명이 지금 설정과 다른 날짜가 "재분류 필요"입니다.
- **이 방식을 고른 이유**: ① 달력·통계는 이미 날짜 요약만 읽는 구조라, 조회할 때마다 원본 10만 건을 다시 분류(방식 A)하지
  않아도 됩니다. ② 기록마다 값을 저장(방식 B)하면 설정을 바꿀 때 원본 테이블을 대량 수정해야 하고, 백업·동기화에 옛
  분류값이 섞여 들어갑니다. 요약만 다시 만들면 원본은 절대 바뀌지 않습니다. ③ 실측(이 저장소 실제 기록 102,632건·16일)
  전체 요약 재생성이 약 0.6초라 설정 변경 때 다시 만들어도 부담이 없습니다.
- **재분류 흐름**: 설정 저장(검증 통과) → `reclassifySummaries()`가 서명이 다른 날짜만 하나씩 다시 만듭니다.
  - **진행 표시**: 설정 탭 하단 `재분류 중… n / m일`(`getClassificationStatus()`의 `progress`를 300ms마다 조회).
    SQLite는 날짜 사이마다 이벤트 루프를 비워서 도는 중에도 진행률 요청에 답합니다.
  - **중복 실행 방지**: 화면 플래그 + 저장소가 이미 돌고 있는 작업(같은 Promise)을 돌려줍니다. 버튼·입력도 잠급니다.
  - **실패 시 보존**: 날짜 요약 한 건을 한 문장(SQLite UPSERT)/한 번의 `put`(IndexedDB)으로 통째로 바꾸므로, 중간에 실패해도
    각 날짜는 예전 요약이거나 새 요약입니다. 원본 기록은 건드리지 않습니다. 남은 날짜는 "지금 재분류"로 이어서 처리됩니다.
  - **종료 후 다시 열기**: 앱 시작 시(SQLite 생성자 `_migrateSummaries` / IndexedDB `init`) 서명이 다른 날짜를 이어서
    재분류합니다.
  - **캐시 무효화**: 완료 후 `refreshDateIndex()`로 달력·일자 요약 캐시를 다시 읽고, 통계는 탭을 열 때 날짜 요약으로 다시
    집계합니다. 재분류 전이면 통계·일자 요약에 "아직 다시 분류하지 않은 날짜" 경고가 뜹니다. 분류 설정만 바꾼 저장은
    누적 지도 Coverage 캐시를 무효화하지 않습니다(무관). 추천 기능·추천 캐시는 아직 없습니다.
- 백업 복원·서버 동기화가 분류 설정을 바꾸면 복원 끝에 같은 재분류를 동기로 실행합니다.

### 구버전 데이터 호환

- **기존 Excel**: 새 열이 필요 없습니다. `시간대`·`날씨` 열이 없는 옛 파일도 Import 되고 시각·GPS로 분류됩니다.
- **기존 SQLite DB / IndexedDB**: 스키마 변경이 없고, 요약 형식 버전(`summary_version` 3 → 4)이 달라 앱을 처음 열 때 날짜
  요약을 한 번 다시 만듭니다(별도 초기화 불필요, 원본 기록·해시 그대로).
- **기존 백업**: 분류 필드·분류 설정이 없어도 복원됩니다. 백업 안에 분류값이 들어 있어도 믿지 않고 다시 계산합니다.
- **중복 판정**: 키(`date|time|vehicle|lat|lng`)와 충돌 비교 필드(`place/road/weather/timeOfDay/traffic/speed`)는 그대로입니다.
  분류는 어느 쪽에도 들어가지 않아, 설정을 바꾸고 같은 파일을 다시 넣어도 새 레코드는 0건입니다.

### 달력 · 통계 · 재생 화면

- **일자 요약**(달력에서 날짜 클릭): `교통 시간대`와 `조도 조건`을 각각 막대 + `N분 · M개`로, 아래에 **조건 조합**(수집 시간
  많은 순 6개)을 축별 배지 `[요일 평일] [교통 퇴근 피크] [조도 일몰 전후] [날씨 비]`로 보여줍니다. 분 단위는 기존 유효 수집
  시간 규칙(차량별 90초 넘는 GPS 공백 제외)이라 두 축 각각의 합이 그날 "수집 시간"과 같습니다.
- **통계 탭**(지역별/차량별 필터 그대로 적용): 교통 시간대 · 조도 조건 · 평일/주말 카드(수집 분 · 기록 수), 분류 기준 안내,
  **구역별(지역 모드) 또는 차량별(차량 모드) × 교통 시간대 / × 조도 조건** 수집 분 표.
- **GPS 리플레이**: 재생 중인 지점의 `교통 · 조도 · 요일 · 날씨`를 배지로 따로 표시합니다.

### 집계 API (향후 추천 입력)

`ConditionStats.aggregate(summaries, { filter, groupBy, signature })` — `summaries`는 `RouteDB.listDateSummaries()` 결과.

- `filter`: `zone` · `vehicle` · `vehicleLike` · `date` · `fromDate` · `toDate` · `weekdayType` · `trafficPeriod` ·
  `lightCondition` · `weather` (조건 축은 값 하나 또는 배열)
- `groupBy`: `zone` · `vehicle` · `weekdayType` · `trafficPeriod` · `lightCondition` · `weather` 중 원하는 조합
- 결과 행: `{ ...묶은 축, recordCount, collectionSec, collectionMinutes, visitCount, lastVisitedAt }` +
  `totals` · `staleDates`(서명이 다른 날짜 수) · `dateCount`. `visitCount` = 그 조합에 기록이 있는 (날짜, 차량) 수,
  `lastVisitedAt` = 마지막 기록 시각(`2026-09-16T18:50:00+09:00` 형식).
- `ConditionStats.fillMissing(rows, { zone: [...], lightCondition: [...] })`로 기록이 없는 조합을 0으로 채워
  "일몰 전후 데이터가 없는 구역", "출근 피크에 가장 적게 주행한 구역"을 구합니다(테스트에 예시 질문 포함).

`groupBy: ['zone','weekdayType','trafficPeriod','lightCondition','weather']` 결과 한 줄 — `tests/time-conditions-test.js`
합성 데이터(9/15 1호·9/16 2호, 강남, 비)의 실제 출력:

```js
{ zone: '강남', weekdayType: 'weekday', trafficPeriod: 'evening_peak', lightCondition: 'sunset', weather: '비',
  recordCount: 102, collectionSec: 3000, collectionMinutes: 50, visitCount: 2, lastVisitedAt: '2026-09-16T18:50:00+09:00' }
```

이 집계 API 를 그대로 쓰는 것이 아래 **추천 주행** 탭입니다(구역·요일·교통 시간대·조도·날씨 조합의 부족도 계산).

## 추천 주행

### 목적

"다음에 어디를, 언제, 몇 번 더 달려야 하는가"를 지금까지 모인 데이터에서 **근거를 가지고** 계산합니다.
임의의 장소를 고르지 않고, 구역·요일·교통 시간대·조도·날씨별 수집량과 Coverage 를 비교해 부족한 조합을 찾습니다.

### 구조 — 순위와 수치는 통계 엔진이 정한다

```
주행기록 DB(날짜 요약의 조건 칸)
→ buildRecommendationFeatures()   구역×요일×교통 시간대×조도×날씨 집계 + 데이터 품질·차량·날씨 목록
→ 후보 생성                        활성 구역 × 평일/주말 × 교통 시간대 × (그 시간대에 실제로 생기는) 조도
→ calculateDeficitScores()        하위 점수 6개(각 0~100)
→ calculateRecommendationScore()  가중합(0~100) · 데이터 없는 항목 제외 후 재정규화
→ estimateCollectionNeed()        권장 시간 범위 · 추가 방문 횟수 · 추가 수집 시간
→ inferEdgeCaseHints()            조건 → 관찰 가능성이 높은 상황(규칙 표·근거 추적)
→ calculateConfidence()           점수와 별개인 "판단에 쓸 데이터가 충분한가"
→ generateRecommendationReason()  템플릿 문장 + 사실 목록(reasonFacts)
→ toLlmPayload() / buildLlmContext()  향후 LLM 에 넘길 구조화 사실
```

- 계산은 전부 `src/js/recommendation.js`(순수 함수, UMD)에 있고 화면(`src/js/recommend-view.js`)은 읽고 그리기만 합니다.
- **LLM 은 이번 구현에 연결돼 있지 않습니다.** 나중에 붙여도 순위·점수·Edge Case 를 만들지 않고 설명·비교만 하도록
  구조화된 사실과 지시문(`buildLlmContext().instructions`)만 넘깁니다.

### 분석 단위와 입력 데이터

분석 단위는 **구역 × 요일 유형 × 교통 시간대 × 조도 조건 × 날씨**입니다. 날짜 요약의 조건 칸(conditionCells)을 더해
만들기 때문에 원본 GPS 기록을 다시 읽지 않습니다(실측: 강남·판교·시흥 활성 구역, 16일·102,632건 기준 후보 66개 생성에 약 45ms).

| 쓰는 데이터 | 출처 |
|---|---|
| 구역·요일·교통 시간대·조도·날씨별 기록 수 · 유효 수집 시간 · 방문 횟수 · 고유 수집일 · 마지막 방문 | 날짜 요약의 조건 칸 |
| 차량별 수집 시간(편중) · 평균/저속/정차 비율 | 조건 칸(차량속도 통계) |
| GPS 공백·점프(품질 경고) · 수집/주행 시간 · KPI·제안 목표 대비 부족량 | 날짜 요약 |
| 구역 Coverage %·유효/미방문 Cell | 누적 지도가 계산해 저장한 **Coverage 스냅샷** |
| 일출·일몰 시각 | 구역 좌표 + 추천 기준 날짜로 계산(time-conditions.js) |

| 쓰지 않는 데이터 | 이유 |
|---|---|
| 교통밀도 열 | 실제 파일에서 값이 대부분 `(미측정)` |
| 도로 유형·어린이보호구역·아파트 인접·교차로 | 기록에 없음(도로종류는 전부 `도심`) — 해당 Edge Case 규칙도 적용하지 않음 |
| 미래 날씨 | 날씨 예보와 연결돼 있지 않음 — "우천 시 우선" 같은 조건 표현까지만 |
| 실제 Edge Case 이벤트(검출·급정거·Cut-in 등) | 아직 수집 항목이 아님 |

`unknown`(시각·GPS·구역을 못 읽은 기록)은 후보 조합으로 만들지 않고, 그 비율만큼 신뢰도를 낮춥니다.

### 추천 점수

```js
recommendationScore =
  timePeriodDeficit * 0.30 + coverageDeficit * 0.25 + lightConditionDeficit * 0.15 +
  weatherDiversityDeficit * 0.15 + staleness * 0.10 + vehicleImbalance * 0.05;
```

| 항목 | 의미 | 계산 |
|---|---|---|
| 시간대 부족도 | 그 구역·요일의 교통 시간대 전체가 목표에 얼마나 못 미치는가 | `100 × (1 − (수집 시간 달성률×0.5 + 방문 횟수 달성률×0.3 + 고유 수집일 달성률×0.2))` |
| Coverage 부족도 | 구역의 도로 칸을 얼마나 못 밟았는가 | `(목표 Coverage − 현재)/목표 × 100` |
| 조도 조건 부족도 | 그 시간대 안의 조도 조건이 부족한가 | 시간대 목표 × (그날 그 시간대에서 해당 조도가 차지하는 비율)로 목표를 나눈 뒤 같은 부족도 식 |
| 날씨 다양성 부족도 | 기록된 날씨 종류에 고르게 모였는가 | 조건 목표를 기록된 날씨 종류 수로 균등 배분해 비교 |
| 최근 미방문 기간 | 마지막 방문 이후 얼마나 지났는가 | `경과 일수 / 기준 일수 × 100`(방문 기록이 없으면 100) |
| 차량 편중도 | 한 차량에 쏠렸는가 | `(최다 차량 비율 − 균등 비율)/(100% − 균등 비율) × 100` |

- 기록 수(GPS 포인트 수)만으로 판단하지 않습니다 — 하루에 한 번 오래 모은 것을 다양하다고 보지 않으려고 **수집 시간 ·
  방문 횟수 · 고유 수집일**을 함께 봅니다.
- **데이터가 없는 항목은 점수에서 빼고**(예: Coverage 계산값 없음, 날씨 기록 없음, 차량 1대) 남은 가중치를 다시 100%로
  나눕니다. 어떤 항목이 왜 빠졌는지는 근거 상세와 카드의 "누락"에 적습니다.
- 목표가 설정되지 않은 시간대는 **같은 구역·같은 요일 유형의 다른 시간대 중앙값**을 비교 기준으로 쓰고, 그 기준을 화면에 적습니다.
- 우선순위: 80~100 매우 높음 · 60~79 높음 · 40~59 보통 · 0~39 낮음.

### 추천 점수 ≠ 신뢰도

- **추천 점수**는 "얼마나 먼저 모아야 하는가", **신뢰도**는 "이 판단에 쓸 데이터가 충분한가"입니다. 따로 계산합니다.
- 높음: 시각·GPS·구역 판정 비율이 높고 수집 기간·비교 조건·Coverage 가 모두 있음
- 보통: 일부 필드 누락, 수집일이 적음(7일 미만), 비교 대상이 적음, Coverage 계산값 없음/임시값, 구역 위치 없음
- 낮음: 시각·GPS·구역을 못 읽은 기록이 30% 초과, 수집일 2일 미만, 품질 경고가 기록 1,000건당 100건 초과
- 낮은 신뢰도 추천도 이유와 함께 표시하며, 설정에서 숨길 수 있습니다.

### 권장 시간 · 횟수 · 수집 시간

- **권장 시간 범위** = 교통 시간대 구간 ∩ 그 조도 구간(추천 기준 날짜 + 구역 좌표로 계산한 일출·일몰 ±설정 분). 5분 단위로
  안쪽 정렬합니다. 일출·일몰 시각은 하드코딩하지 않고 "다음 평일/주말" 날짜로 계산하며, 그 날짜와 일출·일몰 시각을 함께 보여줍니다.
- **추가 방문 횟수** = `max(목표 방문 − 현재 방문, ⌈부족 수집 시간 ÷ 회당 수집 가능 시간⌉)`.
  회당 수집 가능 시간 = 권장 시간 범위 × **수집 효율**(전체 수집 시간 ÷ 주행 시간, 데이터에서 계산).
- 한 번에 너무 많아지면 `추천당 최대 권장 횟수`(기본 3회)로 자르고 "전체 필요 N회 중 이번 M회"로 단계를 알려줍니다.
- 날씨는 예측하지 않습니다 — "날씨가 '비'인 날에 우선 수집" 같은 조건 표현만 씁니다.

### 예상 Edge Case — 가능성일 뿐

카드마다 다음 고지를 함께 보여줍니다: *"예상 Edge Case는 현재 시간대·도로 환경·날씨 조건을 기반으로 한 가능성 추정이며,
실제 발생을 보장하지 않습니다."* 근거 데이터가 없는 규칙은 적용하지 않고, 적용/미적용 규칙과 근거를 근거 상세에 남깁니다.

| 규칙 | 조건 | 적용 여부 |
|---|---|---|
| `MORNING_RUSH_MERGE` 정체·차선 변경·합류·끼어들기 | 출근 피크 | 적용 |
| `LUNCH_SHORT_TRIPS` 단거리 이동·주정차·보행자 | 점심 피크 | 적용 |
| `EVENING_RUSH_CUTIN` 정체·Cut-in 가능성·복잡한 합류 | 퇴근 피크 | 적용 |
| `SUNRISE_LOW_SUN` 저각도 역광·노출 변화 | 일출 전후 | 적용 |
| `SUNSET_GLARE` 역광·급격한 조도 변화 | 일몰 전후 | 적용 |
| `NIGHT_LOW_LIGHT` 저조도·헤드라이트 Glare·인식 거리 감소 | 조도 야간 | 적용 |
| `RAIN_REFLECTION` 노면 반사·차선 가시성 저하·물보라 | 기록에 있는 우천 날씨 | 적용 |
| `SCHOOL_ZONE_ARRIVAL` / `APARTMENT_ADJACENT` / `INTERSECTION` | 어린이보호구역 · 아파트 인접 · 교차로 | **미적용**(해당 데이터 없음) |

차량속도(평균·정차·저속 비율)는 "참고 관찰"로만 적고 정체로 단정하지 않습니다(실제 데이터의 31%가 0km/h = 정차·대기 포함).

### 추천 탭 사용법

1. **추천 요약** — 기준일·데이터 범위·후보 수·우선순위 분포·KPI/제안 목표 대비 부족량
2. **필터·정렬** — 구역 / 평일·주말 / 교통 시간대 / 조도 / 날씨 / 차량 / 최소 신뢰도, 정렬은 추천 점수·Coverage 낮은 순·
   수집 시간 부족 순·마지막 방문 오래된 순(기본: 추천 점수)
3. **추천 카드** — 순위·구역·조건 배지·권장 요일/시간·현재 수집 대 목표·부족한 수집 시간·현재 방문 대 목표·권장 추가 횟수·
   현재 Coverage·미방문 Cell·마지막 방문·부족한 조건·예상 확보 조건·추천 점수·우선순위·신뢰도·추천 이유
4. **근거 보기** — 항목별 현재 상태·점수·가중치·적용 가중치·반영 점수 표(합이 최종 점수와 맞아 검산 가능), 목표·비교 기준,
   권장 시간 계산 근거, 적용/미적용 Edge Case 규칙, 데이터 범위·누락·신뢰도 이유, LLM 전달용 JSON
5. **현재 데이터 부족 현황** — 구역별(수집·방문·수집일·마지막 방문·Coverage), 교통 시간대별 목표 대비, 평일/주말·조도·날씨·차량 분포
6. **추천 설정**, 7. **데이터 한계·신뢰도 안내**

카드 버튼: `이번에는 숨기기`(저장하지 않음) · `N일간 제외` · `수집 완료로 표시` · 숨김 목록에서 `다시 추천받기`.
**수집 완료로 표시해도 주행 기록은 바뀌지 않습니다.** 그때의 실제 수집량을 함께 저장해 두고, 새 데이터가 들어오면
목표를 채웠는지 비교해서 채웠으면 계속 숨기고, 아직 모자라면 "다시 추천"으로 되살립니다.

### 추천 설정

가중치 6개 · 교통 시간대별 목표 수집 시간/방문 횟수 · 기본/구역별 목표 Coverage · 최소 고유 수집일 · 오래된 방문 기준 일수 ·
추천당 최대 권장 횟수 · 추천 결과 개수 · 기간 제외 일수 · 낮은 신뢰도 표시 여부. `기본값 복원` 버튼이 있고, **가중치 합계가
100%가 아니거나 값이 범위를 벗어나면 저장하지 않고 이유를 표시**합니다(저장소도 같은 검증을 다시 합니다).
설정을 바꿔도 원본 주행 기록은 바뀌지 않습니다. 목표 기본값(피크 240분·4회 등)은 데이터에서 나온 값이 아니라 첫 버전의
정책값이라, 운영 목표에 맞게 바꿔 쓰는 것을 전제로 합니다.

### 캐시와 자동 갱신

추천 캐시 키에는 `데이터 · 구역 · 수동 Coverage 셀 · Coverage 스냅샷 · 시간 분류 기준 · 추천 설정` revision 과 차량 필터,
오늘 날짜(한국 기준)가 들어갑니다. revision 은 저장소 변경 알림으로만 올라가서, **탭을 오가기만 하면 DB 조회도 재계산도
하지 않습니다.** 다시 계산하는 경우: Import · 삭제 · 백업 복원 · 서버 동기화 · 구역/경계 변경 · 수동 방문·미방문 셀 변경 ·
Coverage 재계산 · 시간대/조도 설정 변경 · 재분류 · 추천 설정 변경 · 날짜가 바뀐 경우. 필터·정렬·숨김/완료 처리는 다시 계산하지
않고 목록만 바꿉니다. 늦게 끝난 예전 계산은 최신 결과를 덮지 않습니다.

Coverage 스냅샷은 누적 지도에서 "커버리지 갭 보기"로 계산할 때 저장됩니다(전체 기간 계산만). 저장할 때 데이터·경계·수동 셀
지문을 함께 적어 두고, 그 뒤 무엇이든 바뀌면 "오래됨"으로 보고 **Coverage 항목을 점수에서 빼고 신뢰도를 낮춥니다**.

### 주행 계획으로 이어보기

추천 카드는 "무엇이 부족한가"까지입니다. 그걸 **오늘 몇 시부터 어디로** 로 바꾸려면 같은 탭 위쪽의
[주행 계획](#주행-계획--그-시간에-나가면-어디부터-어떻게-돌까)을 쓰세요 — 같은 점수 규칙을 그대로 써서
운행 시간을 블록으로 나눠 배치합니다.

### 향후 확장

- **실제 Edge Case 로그**: 추천 데이터 모델에 `observedEdgeCases`(지금은 항상 빈 배열) · `predictedEdgeCaseHints` ·
  `edgeCaseEvidenceLevel`(지금은 `condition_only`)이 이미 있습니다. 검출 수·급정거·TTC·Cut-in·불법 주정차·공사 구간·
  신호/차선 인식 실패·센서 이상·수동 개입 로그가 들어오면 `observedEdgeCases` 를 채우고 근거 수준을 올리는 방향으로 넓힐 수 있습니다.
- **LLM 연결**: `Recommendation.toLlmPayload(추천)` 과 `buildLlmContext(결과, 추천들)` 이 구조화된 사실만 만듭니다.
  원본 GPS 좌표·사람 이름·차량 이름은 넣지 않습니다(테스트로 확인). LLM 은 이 결과를 설명·비교·질의응답에만 쓰고,
  순위·수치·Edge Case 를 새로 만들지 않도록 지시문을 함께 넘깁니다.

## 주행 계획 — "그 시간에 나가면 어디부터 어떻게 돌까"

추천 카드가 **무엇이 부족한가**를 말한다면, 주행 계획은 그 답을 **하루 일정**으로 바꿉니다.
추천 탭 위쪽 "주행 계획"에서 운행 시간을 바꿔 보면 바로 다시 계산됩니다(계산은 즉시 끝납니다).

### 무엇을 입력하나

| 입력 | 기본값 | 설명 |
|---|---|---|
| 요일 | 평일 | 평일/주말에 따라 부족한 조건이 다릅니다 |
| 운행 시작 · 종료 | 09:00 ~ 18:00 | 바꿔 보고 싶은 시간 |
| 비교 기준 | 09:00 ~ 18:00 | **지금** 운행 시간 — 이것과 견줘서 무엇이 달라지는지 보여줍니다 |
| 차량 | 1대 | 여러 대면 같은 시간에 서로 다른 구역으로 나눕니다 |
| 구역 | 전부 | 오늘은 강남만 돌 것처럼 일부만 고를 수 있습니다 |

프리셋 버튼: **1시간 일찍 시작 · 1시간 늦게 종료 · 앞뒤 1시간씩 · 기본으로**.

### 어떻게 계획을 세우나 (순서대로)

1. 운행 시간을 **교통 시간대 경계**(출근 피크 07~10 …)와 **그날의 일출·일몰 경계**로 자릅니다.
   너무 긴 구간은 60분으로 나누고, 15분보다 짧은 꼬리는 앞 블록에 붙입니다.
2. 블록마다 그 시각의 조건(교통 시간대 · 조도)을 정하고, **그 조건에서 가장 부족한 구역**을 고릅니다 —
   점수는 추천 카드와 **같은 규칙**(부족도 점수)을 그대로 씁니다.
3. 조건 한 칸의 **남은 부족분을 장부처럼 깎아 나갑니다**. 한 칸을 채우면 자연히 다음으로 부족한 곳으로 옮겨갑니다
   (목표를 다 채운 칸에 하루 종일 머무르지 않습니다).
4. 구역을 옮기면 **이동 시간만큼 수집 시간이 줄어드는 것**을 값에 반영합니다 — 이동해서 얻는 것이 더 클 때만 옮깁니다.
   이동 시간 = 구역 중심 사이 직선 거리 ÷ 평균 속도(기본 30km/h)로 잡은 어림값입니다.
5. 같은 계산을 **비교 기준 운행 시간**으로 한 번 더 해서 차이를 냅니다.

### 무엇을 보여주나

- 시각별 표: `08:00~09:00 · 강남 · [교통: 출근 피크] [조도: 주간] · 수집 60분 · 이동 —분 · 이유`
- 요약: 예상 수집 시간 · 이동 시간 · 구역별 시간 · 그날의 일출/일몰
- 비교: `지금(09:00~18:00)보다 60분 더 모읍니다` + **새로 잡히는 조건**과 그 조건의 부족분을 얼마나 메우는지,
  반대로 **빠지는 시간**이 있으면 그것도 함께.

### 하지 않는 것 (한계)

- 이동 시간은 직선 거리 어림값입니다 — 실제 도로·신호·주차 시간은 반영하지 않습니다.
- 계획의 수집 시간은 "그 시간에 그 구역에 있으면 계속 기록된다"고 본 **최대치**입니다(휴식·신호 대기를 빼지 않습니다).
- 날씨는 예측하지 않습니다. 구역 좌표가 없으면 조도(일출·일몰)를 계산하지 못하고 교통 시간대만으로 계획하며,
  그 사실을 화면에 적습니다.
- 순위·수치는 전부 통계 규칙이 정합니다(LLM 이 정하지 않습니다).

## Import 이슈 기록 · 이슈 데이터 분리

### 왜 필요한가

주행기록 파일 중에는 "이건 좀 이상한데" 싶은 것이 섞입니다(GPS 가 튀거나, 테스트 주행이 섞였거나, 차량이 잘못
기록됐거나). 그렇다고 지워버리면 되돌릴 수 없고, 그냥 두면 그 데이터가 수집 현황·Coverage·추천 계산에 조용히
섞여 들어갑니다. 그래서 **지우지 않고 표시만 해 두고, 볼 때 골라서 거르는** 방식으로 다룹니다.

### 저장하기 전에 한 번 묻는다

파일을 끌어놓거나 골라서 불러오면, 저장 전에 확인 창이 한 번 뜹니다. 파일마다

- 파일명 · 예상 날짜 · 차량 · 레코드 수(이미 넣었던 파일이면 그렇다고 알려줍니다)
- **이 파일에 이슈가 있어요 (확인 필요)** 체크박스
- 이슈 내용 한 줄 메모(최대 200자)

를 보여주고, **취소**하면 아무것도 저장하지 않습니다. 이슈를 체크했는데 메모가 비어 있으면(공백만 있어도)
그 자리에서 막고, **파일 하나라도 어긋나면 전부 저장하지 않습니다**. 여러 파일을 한 번에 넣어도 이슈는
파일마다 따로 붙습니다 — 한 파일의 이슈가 다른 파일로 번지지 않습니다.

### 이슈는 메모가 아니라 데이터에 이어진다

중복 제거 때문에 같은 GPS 기록이 여러 파일에서 올 수 있습니다(A.xlsx 이슈 있음 / B.xlsx 정상). 그래서 이슈를
Import 이력에만 적어두면 "이 기록이 이슈 파일에서 왔는지"를 알 수 없습니다. 기록과 파일의 관계를 따로
저장합니다.

- SQLite: `record_sources(record_hash, import_id)` — 새로 들어간 기록과 **중복이라 걸러진 기록 모두** 기록합니다.
- IndexedDB: `recordSources` 저장소(같은 뜻, id = `레코드 키 + importId`).
- 날짜 요약의 조건 칸(`conditionCells`)에는 그 칸의 **이슈 마스크**가 함께 저장됩니다
  (`1` 이슈 없는 파일 · `2` 확인 필요 · `4` 확인 완료 · `0` 출처 기록이 없는 예전 데이터, OR 로 겹칩니다).
  덕분에 달력·통계·추천은 원본 기록을 다시 읽지 않고도 상태별로 나눠 셀 수 있습니다.

### 데이터 상태 필터 — 세 가지 의미

판정 규칙은 `src/js/issue-filter.js` 한 곳에 있습니다(SQLite 는 같은 뜻의 `EXISTS` SQL, IndexedDB 는 마스크로
판정하고, 두 결과가 같은지 테스트로 확인합니다).

| 값 | 화면 이름 | 의미 |
|---|---|---|
| `all` | 전체 | 이슈 여부와 상관없이 모두 |
| `clean` | 이슈 없음 | **확인 필요 이슈 파일에서만** 온 기록을 뺍니다. 정상 파일이나 확인 완료 파일에서도 왔다면 남깁니다 |
| `issue_all` | 이슈만 | 이슈로 표시한 파일에서 온 기록 |

필터는 이 셋뿐입니다. **확인 필요 / 확인 완료는 이슈의 처리 상태이지 따로 볼 데이터 묶음이 아닙니다** —
필터로 만들어 두면 '이슈 없음'·'이슈만'과 뜻이 겹쳐서 지금 무엇을 보고 있는지 헷갈립니다. 상태는
달력 배지·일자 요약·데이터 관리 목록에서 보고 바꿉니다(바꾸면 '이슈 없음'에 들어오고 나가는 데이터가 달라집니다).
예전 버전에서 저장해 둔 `issue_open`/`issue_resolved` 값은 '이슈만'으로 읽습니다.

- 한 기록은 어떤 필터에서도 **한 번만** 셉니다(출처가 여럿이어도 중복 집계하지 않습니다).
- 한 기록이 이슈 파일과 정상 파일 양쪽에서 왔다면 '이슈 없음'과 '이슈만' 양쪽에 나옵니다 —
  그래서 상태별 합이 전체보다 클 수 있습니다(통계 화면에 그렇게 적혀 있습니다).
- 고른 값은 브라우저/앱에 남아서 탭을 옮기거나 다시 켜도 유지됩니다.

### 화면별로 어떻게 보이나

- **달력**: 이슈가 있는 날짜에 `확인 필요 n` / `확인 완료 n` 배지. 필터를 걸면 그 기준으로 지점 수·수집 시간이
  다시 계산되고, 남는 기록이 없는 날짜는 흐려집니다. **주행 시간(첫 기록~마지막 기록)은 파일별로 쪼갤 수 없어서**,
  하루가 일부만 걸러진 날짜는 주행 시간 합계에서 빠지고 그 사실을 표 아래에 적습니다.
- **일자 요약**: "이슈사항" — 그 날짜 기록이 어느 파일에서 왔는지 목록과 함께, 메모 수정 · 확인 완료로 변경 ·
  이슈 해제를 할 수 있습니다.
- **누적 지도**: 구역 색 점은 **언제나 그대로 그리고**, 그 위에 이슈 몫만큼만 회색 점을 겹쳐 올립니다.
  그래서 같은 자리에서 문제 없는 날과 문제 있는 날을 모두 달렸으면 **두 색이 함께 보입니다**(회색 점의 크기는
  그 칸에서 이슈 기록이 차지하는 비율 √ 이고, 전부 이슈인 칸만 완전히 회색이 됩니다). 지도 아래에 회색 점이
  몇 칸인지 안내가 뜨고, 칸 위에 커서를 올리면 그 칸의 이슈 기록 수를 알려줍니다. '이슈 없음'을 보고 있을 때는
  겹치지 않습니다 — 그 화면에 남은 기록은 정상 파일에서도 나온 것들이라 회색으로 표시할 이유가 없습니다.
- **누적 지도 · Coverage**: 같은 필터 버튼이 있고, **Coverage 캐시 키에 필터가 들어갑니다**
  (`coverageCalcKey`). 구역 경계·도로/건물 같은 정적 계산 키(`coverageGeometryKey`)에는 넣지 않아서,
  필터를 바꿔도 지도 데이터를 다시 받아오지 않습니다. 필터를 되돌리면 이전 계산 결과를 그대로 재사용합니다.
- **통계**: "이슈 현황"과 전체 / 이슈 없음 / 이슈 데이터 비교표. 구역·차량·장소·도로종류·날씨·시간대 막대와
  교통 시간대·조도·요일 막대에는 **이슈 데이터 몫이 같은 막대 안에 회색으로 겹쳐** 그려지고, 카드 아래에
  회색이 몇 개(몇 분)인지 적힙니다. 지도의 회색 점과 같은 색(`#7d8798`)입니다. 막대의 나머지 부분은
  고른 지역·차량의 색을 씁니다(교통 시간대·조도·요일 카드도 같은 색 규칙을 따릅니다).
- **데이터 관리**: "이슈 관리" — 파일명·메모 검색, 이슈만 보기, 상태별 보기, 메모 수정, 확인 필요 ↔ 확인 완료,
  이슈 해제(표시만 지우고 GPS 기록은 그대로 둡니다).
- **추천 주행**: 기본적으로 **확인 필요 이슈 데이터를 빼고** 계산하고, 화면에 `추천 계산 기준: 확인 필요 이슈
  데이터 제외`라고 적습니다. 아직 확인하지 않은 데이터로 "여기는 이미 충분하다"고 판단하지 않기 위해서입니다.
  이슈 데이터까지 포함해 보려면 '이슈만'·'확인 필요' 필터를 고르면 됩니다. 누적 지도가 저장한 Coverage 스냅샷이
  다른 데이터 상태로 계산된 값이면 한계 목록에 적고 신뢰도를 한 단계 낮춥니다.

### 성능 — 레코드마다 출처를 훑지 않는다

이슈 필터를 `EXISTS (record_sources 조인)` 으로 판정했더니 10만 건짜리 DB에서 화면 하나 여는 데 **7초**가
걸렸습니다(실측). 지금은 레코드마다 출처 마스크를 `driving_records.issue_mask` 에 저장해 두고, 조회는 비트
연산만 합니다.

- 마스크는 Import 직후(그 파일의 레코드에 비트를 OR)와 이슈 수정·복원 직후(그 파일의 레코드만 다시 계산)에만
  갱신합니다. 예전 DB 를 열면 컬럼을 붙이면서 한 번 전부 계산합니다.
- 이슈로 표시한 파일이 하나도 없으면 필터 조건을 아예 걸지 않습니다(전체 = 이슈 없음, 이슈 데이터 0건).
- Import 이력의 "파일별 레코드 수"는 데이터 관리 화면에서만 셉니다(`withRelatedRecords`).

실측(10만 건 · 파일 31개 · 이슈 5개): 전체 조회 127ms · 이슈 없음 7,112→**570ms** · 누적 지도 밀도 3,352→**331ms** ·
이슈 현황 2,144→**152ms**.

### 성능 — 화면 하나에 조회 한 번 (브라우저 모드)

브라우저 모드(IndexedDB)에는 SQL 이 없어서 **집계마다 전체 기록을 커서로 훑습니다**(8만 건에 약 0.4초).
통계 탭이 요약·장소·도로·날씨·시간대·이슈 몫·이슈 현황을 따로 물어보면 같은 8만 건을 열 번 넘게 훑어서
탭 한 번에 5초가 넘게 걸렸습니다. 그래서 **화면이 필요한 값을 한 번에 주는 묶음 API** 를 뒀습니다.

| API | 주는 것 | 브라우저 모드 스캔 |
|---|---|---|
| `getStatsBundle(filter, {withIssueShare, withIssueOverview})` | 요약 + 구역/차량/장소/도로/날씨/시간대 분포 + 그중 이슈 몫 + 이슈 현황 | **0번**(날짜 요약만 읽음) |
| `getAccumBundle(filter, cell)` | 요약 + 밀도 칸(이슈 몫 포함) + 지도 범위 | 1번 |
| `getIssueOverview(filter)` | 전체/이슈 없음/이슈 데이터 기록 수 + 출처 없는 기록 수 | 1번 |

통계 탭은 아예 원본 기록을 읽지 않습니다. 날짜 요약에 **분포 칸(`distCells`)** — 구역·차량·장소·도로종류·날씨·
파일 원본 시간대·이슈 마스크 조합별 기록 수 — 를 같이 저장해 두고, 통계는 그 수십 줄만 더합니다
(하루치 조합은 보통 수십 줄입니다). 요약 형식이 바뀌었으므로 예전 요약은 앱을 켤 때 한 번 다시 만듭니다
(`SUMMARY_VERSION 7`). 분포 칸이 아직 없는 날짜가 섞여 있으면 그때만 예전처럼 원본 기록으로 셉니다.

SQLite(데스크톱)는 같은 API 를 색인을 쓰는 SQL 로 답합니다 — 이슈 몫은 같은 `GROUP BY` 안에서 조건부 SUM 으로
세기 때문에 쿼리가 두 배로 늘지 않습니다. 저장소가 달라도 화면 코드는 같은 한 번의 호출만 합니다.

실측(8만 9천 건, 브라우저 모드): 통계 탭 5.3초 → 0.64초 → **7ms**(요약 기반) · 누적 지도 1.2초 → **0.44초**.
데스크톱(SQLite)도 같은 길을 씁니다 — 통계 묶음 466ms → **28ms**.

### 성능 — 지도 데이터 서버가 막혀 있을 때

Coverage 판정에 쓰는 도로·건물 데이터는 Overpass(무료 커뮤니티 서버)에서 받아옵니다. 미러 4개를 15초씩
순서대로 기다리도록 돼 있어서, 이 데이터를 못 받는 네트워크에서는 한 번 계산에 최대 1분이 걸렸고
**탭에 들어올 때마다 그걸 반복**했습니다(임시 결과는 다시 들어올 때 재시도하게 돼 있습니다).

- 미러당 대기를 **8초**로 줄이고,
- 미러가 전부 실패하면 **10분 동안은 아예 시도하지 않습니다**(그동안은 도로·건물 없이 바로 계산 — 결과는
  여전히 "임시"로 표시되고 추천 신뢰도도 낮춥니다).
- 왜 대체값으로 그렸는지와 언제 다시 시도하는지 안내 문구로 알려주고, **"커버리지 갭 보기"를 직접 누르면**
  "지금 다시 해봐"로 보고 곧바로 재시도합니다.

### 백업 · 서버 동기화

- 백업에는 Import 이력의 이슈(체크 여부·메모·상태·시각)와 **그 파일에서 나온 레코드 키**가 함께 들어갑니다.
- 복원·동기화 때 같은 Import 인지는 `파일명 | 파일 지문 | Import 시각`으로 가립니다(기기마다 id 가 다르므로).
- 이슈가 양쪽에서 다르게 수정됐으면 **`issueUpdatedAt` 이 최신인 쪽을 남기고, 메모를 임의로 합치지 않습니다**.
  밀려난 값은 `issueConflict` 로 남겨 데이터 관리·일자 요약에서 볼 수 있습니다.
- 레코드 출처(recordKeys)는 양쪽을 합집합으로 모읍니다 — 한쪽만 남기면 출처가 끊깁니다.
- 백업 복원이 만드는 `(백업 복구)` Import 는 **출처로 남기지 않습니다**. 남기면 모든 기록이
  "이슈 없는 파일에서도 왔다"가 되어 이슈 분리가 통째로 무너집니다(진짜 출처는 백업 안의 Import 이력이 되살립니다).

### 예전 데이터

이 기능 이전에 들어온 기록에는 출처 정보가 없습니다(마스크 `0`). 이런 기록은 **전체·이슈 없음 화면에 그대로
보이고**, 이슈 화면에는 나오지 않습니다 — 이슈라고 단정하지도, 지도에서 갑자기 사라지지도 않습니다.
출처 없는 기록이 몇 건인지는 통계의 이슈 현황에서 알려줍니다. 이슈 필드가 없던 예전 백업도 그대로 복원됩니다.

## 누적 지도 — 날짜 필터

- **기본값은 언제나 "전체 기간"** 입니다. 앱을 켜고 누적 지도에 처음 들어가면 날짜칸을 비우고 시작합니다
  (Chromium 이 새로고침 때 입력값을 되살리는 일이 있어서, 화면 값과 조회 조건이 어긋나지 않게 같이 비웁니다).
- **사용법**: 누적 지도 상단의 시작일·종료일 칸에서 날짜를 고르거나 키보드로 입력합니다(예: `20260901`).
  입력이 멈추고 0.6초 뒤 자동 적용되고, **Enter** 또는 **날짜 적용** 버튼은 바로 적용합니다.
  **지난달**은 지난달 1일~말일, **날짜 초기화**는 날짜 조건을 지우고 전체 기간으로 되돌립니다.
- **표시 기간** 라벨: `표시 기간: 전체 기간` · `표시 기간: 2026-09-01` · `표시 기간: 2026-09-01 ~ 2026-09-05` ·
  `표시 기간: 2026-09-03 ~ (최신)` · `표시 기간: (처음) ~ 2026-09-03`
- 범위는 **시작일과 종료일을 모두 포함**합니다. 시작일만 → 시작일부터 최신까지, 종료일만 → 처음부터 종료일까지.
  날짜 조건이 걸리면 `날짜미상` 기록은 빠집니다. 시작일이 종료일보다 늦으면 서로 바꿔 적용하고 안내하며,
  연·월·일을 끝까지 입력하지 않은 칸은 적용하지 않고 안내합니다. 같은 범위를 다시 적용하면 아무것도 다시
  계산하지 않습니다.
- **같은 날짜 범위가 적용되는 곳**
  - 밀도 지도: 지도 Cell, Cell별 기록 수와 색·크기, 누적 일수, 총 기록 지점, 구역별/차량별 기록 수, 지도 화면 맞춤, 호버 툴팁
  - Coverage Map: 실제 GPS 방문 Cell, GPS 구간 보간으로 방문 처리된 Cell, 방문 횟수, 방문/미방문 판정, 빨간 미방문 칸,
    Coverage %, 전체/방문/미방문 Cell 수, Coverage Depth
  - 조회 조건은 SQLite(`_filterSql`, `getCellVisitCounts`)와 IndexedDB(`matches`)가 같습니다:
    `date >= 시작일 AND date <= 종료일`, `YYYY-MM-DD` 형식 날짜만.
- **"날짜를 바꿔도 전체 기간이 그대로" 보이던 원인**(수정됨): ① 날짜칸에 `max`가 없어 Chromium이 연도를 6자리까지
  받았습니다 — 키보드로 `20260901`을 치면 연도가 202609가 되고 월·일이 비어 값이 `''`로 남아 필터가 적용되지 않았습니다.
  지금은 `min="2000-01-01" max="2099-12-31"`로 연도를 4자리로 제한합니다. ② 날짜칸 `change`가 입력 도중에도(24일을
  치면 "2"에서 2일로) 와서 그때마다 다시 계산하는 사이 이어 치던 숫자가 엉뚱하게 들어갔습니다 — 지금은 debounce.
  ③ 시작일만 걸면 `날짜미상` 기록이 섞였습니다. ④ 브라우저(IndexedDB) 모드는 3.1.2 초기까지 날짜 조건을 무시했습니다
  (커밋 3ce67f5에서 수정).

## 📷 현재 지도 캡처

- 누적 지도 상단 **📷 현재 지도 캡처**를 누르면 지금 보이는 지도가 PNG로 저장됩니다.

| | 데스크톱 앱 (Electron) | 브라우저 모드 (`node server.js` → `/src/index.html`) |
|---|---|---|
| 방식 | 메인 프로세스가 `webContents.capturePage(지도 영역)` | 화면에서 배경 타일 `<img>` + Leaflet Canvas Layer를 캔버스에 합성 → `toBlob` |
| 저장 | 저장 대화상자(기본 위치: 사진 폴더) | 파일 저장 창(`showSaveFilePicker`, Chrome/Edge)으로 위치·이름 선택 — 지원하지 않거나 띄울 수 없으면 브라우저 다운로드 폴더 |
| 창보다 큰 지도 | 보이는 부분만(안내) | 지도 전체 |

- **데스크톱 방식**: 화면이 지도 DOM의 화면 좌표와 기본 파일명을 IPC(`routeAPI.captureMap`)로 넘기면 메인 프로세스가
  `webContents.capturePage(지도 영역)` → PNG 변환 → 저장 대화상자 → 파일 쓰기를 합니다. 화면에 실제로 그려진 픽셀을
  찍으므로 CORS나 Canvas Layer 누락 문제가 없습니다. 화면 코드는 파일 경로를 직접 다루지 않고, preload에는
  `captureMap` 하나만 추가됐습니다.
- **브라우저 방식**: `html2canvas` 같은 DOM 복제 대신 Leaflet이 이미 그려 둔 것만 합친다 —
  ① 줌 단계별 타일 묶음을 z-index 순서로(이전 줌 단계의 확대된 타일이 위에 겹치지 않게), 화면과 같은 CSS filter
  (`.leaflet-tile-pane`의 흑백·밝기)를 걸어서 ② 그 위에 Leaflet Canvas Layer(`preferCanvas` — 칸·원·경계선 전부)
  ③ 지도 저작권 표시를 글자로. 화면 배율(`devicePixelRatio`)만큼 선명하게 만듭니다.
  - 배경 타일(`tile.openstreetmap.org`)은 `Access-Control-Allow-Origin: *`를 보내므로 누적 지도 타일을
    `crossOrigin:'anonymous'`로 받아 캔버스가 오염되지 않습니다. 타일 서버를 CORS를 허용하지 않는 곳으로 바꾸면
    "CORS를 허용하지 않아 이미지를 만들 수 없어요" 오류가 납니다.

#### 배경 타일 서버 — 왜 OSM 이고, 왜 User-Agent 를 바꾸나

OSM 공식 타일 서버는 자원봉사가 운영해서 [타일 사용 정책](https://operations.osmfoundation.org/policies/tiles/)이
**앱을 식별할 수 있는 User-Agent** 를 요구합니다. Electron 기본 UA 로 요청하면 타일 대신 "Access blocked" 403
이미지가 오고(응답에 `x-blocked: Access denied` 헤더) 지도가 노란 빗금으로 덮입니다. 그래서 데스크톱 앱은
`electron/osm-tile-ua.js` 의 `applyOsmTileUserAgent()` 로 **타일 요청에만** UA 를 바꿔서 보냅니다
(Overpass 등 다른 요청은 건드리지 않습니다).

**브라우저 모드는 브라우저가 OSM 에 직접 가지 않습니다.** `server.js` 가 `/tiles/z/x/y.png` 로 타일을 대신 받아
주는 프록시를 둡니다 — 앱 식별 UA 로 OSM 에 요청하고, 받은 타일은 `tile-cache/`(git 제외)에 7일간 캐시합니다.
브라우저가 직접 받던 때에는 **새 프로필 Edge 는 통과하는데 사용자 PC 의 Edge 는 "Access blocked"** 를 받는 일이
있었고, 그 차이(프로필·캐시·Referer 등)는 밖에서 관찰도 수정도 할 수 없었습니다. 프록시를 거치면 브라우저 상태와
무관해집니다. OSM 이 거절하면(`x-blocked` 헤더 · 4xx/5xx · 이미지 아닌 응답) 캐시하지 않고 502 를 주며 서버 창에
`[tiles] OSM 이 타일 z/x/y 를 거절: …` 로그를 남깁니다(10초에 한 줄로 묶음). 예전에 받아 둔 타일이 있으면 오래됐어도
그걸 줍니다. 프록시가 못 준 칸만 화면이 OSM 에서 직접 받아 봅니다.

실측값(강남 z14 타일): 차단 이미지 **6,987바이트** / 정상 타일 **43,121바이트**.

- 지도가 노란 빗금 + "Access blocked" 로 덮이면 → 데스크톱은 UA 주입이 빠진 것, 브라우저 모드는 서버 창의
  `[tiles]` 로그부터 봅니다(로그가 없으면 화면이 `/tiles` 를 쓰지 않는 것 — 서버 없이 연 경우 등).
- 타일에 **"API KEY REQUIRED"** 워터마크가 찍히면 → 키가 필요한 상용 타일(CARTO 등)로 바뀐 것입니다.
- **둘 다 HTTP 200 으로 옵니다.** 상태 코드만 확인해서는 절대 못 잡고, 타일 그림을 직접 봐야 압니다
  (실제로 겪은 회귀: 200 만 보고 CARTO 로 바꿨다가 지도 전체에 워터마크가 찍혔습니다).
  - `ctx.filter`를 지원하지 않는 브라우저(Safari)에서는 배경 지도가 흑백 필터 없이 원본 색으로 저장됩니다.
- **포함**: 지금 중심·줌·범위, 선택 구역, 날짜 범위, 밀도 지도 또는 Coverage Map(방문/미방문 칸, 적용 완료된 수동
  방문·미방문·제외 상태), 구역 경계, 배경 지도 타일, 지도 저작권 표시.
- **제외**(캡처하는 동안만 숨기고 끝나면 `finally`에서 되돌림): 적용 전 선택(pending) 미리보기, 확대/축소 버튼,
  호버 툴팁, 로딩 표시, 경계 꼭짓점 핸들. 날짜 입력칸·편집 버튼은 지도 영역 밖이라 들어가지 않습니다.
- **파일명**: `RouteViewer_<구역>_<기간>_<모드>_<YYYYMMDD_HHMMSS>.png`
  - 기간: `전체기간` · `20260901` · `20260901-20260905` · `20260901부터` · `20260905까지`
  - 모드: `Density` · `Coverage` · `CoverageDepth`
  - 예: `RouteViewer_강남_전체기간_Coverage_20260911_142530.png`. 파일명에 쓸 수 없는 문자는 지웁니다.
- **상태 처리**: 지도를 그리는 중(날짜를 바꾼 직후 포함)에는 버튼이 비활성이라 이전 지도를 찍지 않습니다. 캡처 직전
  `invalidateSize()`를 하고 줌/이동 애니메이션과 배경 타일 로딩이 끝나기를 최대 8초 기다립니다(그래도 로딩 중이면
  저장 후 안내). 지도가 스크롤 아래에 걸쳐 있으면 잠시 화면 안으로 스크롤했다가 되돌립니다(창보다 큰 지도는 보이는
  부분만 저장하고 안내). 중복 클릭은 무시하고, 저장 취소는 오류로 표시하지 않으며, 저장 실패는 오류 메시지로 알립니다.
- 캔버스 PNG를 만들 수 없는 아주 오래된 브라우저에서만 버튼이 비활성이고 안내만 합니다.
- 인터넷이 끊겨 배경 타일을 못 받으면 캡처에도 타일이 비어 있습니다(지도에 보이는 그대로 저장).

## Coverage Map

### 판정 규칙

- **Coverage Cell 크기: 20m 고정.** 화면(`src/js/accum.js`의 `GAP_CELL_SIZE_M`), SQLite, IndexedDB가 모두
  `src/js/coverage-grid.js`의 `DEFAULT_CELL_SIZE_M = 20` 하나를 기준으로 씁니다. 사용자 설정값이 아닙니다 —
  설정(`getSettings()`)의 `coverageCellSizeM`은 항상 20을 돌려주고, 예전 버전이 50을 저장해 뒀어도 무시하며,
  `setSettings()`는 이 값을 저장하지 않습니다.
- **유효 Cell** = 구역 경계(직접 그린 polygon) 안 + 주행 도로 칸 − (아파트 단지 ∪ 주차장 ∪ 건물 mask) − 수동 제외 칸.
  - 도로: 강남(및 사용자가 만든 "서초")은 `src/data/hdmap_*_roads.js`의 HD map, 그 외 구역은 OSM Overpass에서
    주행 도로(`highway` whitelist)를 받아 씁니다. 끊긴 도로 끝점은 자동 연결(gap healing)합니다.
  - 건물/아파트/주차장: Overpass에서 구역 bbox만 받아 `localStorage`에 캐시합니다.
- **방문 횟수**: 같은 `(date, vehicle)` 안에서 시간순으로 이어진 두 GPS 점 사이 이동 경로가 지나간 칸을 모두
  방문으로 셉니다(`CoverageGrid.accumulatePartitionVisits`, SQLite·IndexedDB 공용). 같은 칸에 연속으로 찍힌 점은
  방문 1회, 칸을 벗어났다 돌아오면 새 방문입니다. 시간차 30초 초과 또는 150km/h 초과면 사이를 잇지 않습니다.
- **Coverage % = 방문 Cell / 유효 Cell.** Coverage Depth는 방문 횟수를 등급(기본 미수집 0 / 부족 1 / 보통 2~4 /
  충분 5+)으로 나눠 보여줍니다.

### 수동 셀 편집 (⚙️ 패널)

| 버튼 | 의미 |
|---|---|
| 🗑️ 제외 셀 선택 | 이 칸은 도로가 아님 → Coverage 대상(유효 Cell)에서 뺌 |
| ✅ 방문 셀 선택 | 이 칸은 방문한 것으로 침 → 방문 횟수 최소 1 |
| 🔴 미방문 셀 선택 | GPS가 지나갔거나 실수로 방문 처리된 칸을 미방문으로 침 → 방문 횟수 0 (빨간 칸, Depth "미수집") |
| 선택 적용 (N) | **이번에 찍은 칸(N개)만** 저장하고 그 구역 Coverage만 다시 계산 |
| 현재 구역 선택 초기화 | **아직 적용하지 않은 이번 선택(미리보기)만** 지움 |

- 상태는 두 층으로 나뉩니다.
  - **확정 상태** — DB에 저장된 `{excluded, visited, unvisited}`. 칸을 클릭해도 바뀌지 않습니다.
  - **현재 선택(pending)** — `cellKey → {lat, lng, targetState}` (`targetState`: `exclude | visited | unvisited | none`).
    지도에는 확정 상태 위에 미리보기로 겹쳐 그립니다.
- 칸 클릭은 pending만 토글합니다. 같은 모드로 다시 누르면 취소되고, 이미 그 상태로 확정된 칸을 누르면
  "해제 예정(none)"이 됩니다. 클릭 자체는 DB에 저장하지 않습니다.
- **선택 적용**: pending이 비어 있으면 아무것도 안 함 → 확정 상태 복사본에 pending만 병합 → 한 칸이 여러 상태에
  들어가지 않게 정규화 → **DB 저장 1회** → 저장 성공 후에만 확정 상태 교체 → pending 비움 → 편집 모드 종료 →
  그 구역 캐시만 무효화 후 재계산. **저장이 실패하면** 확정 상태와 pending을 그대로 두고 오류를 보여주며, 다시
  적용할 수 있습니다.
- **현재 구역 선택 초기화**: pending과 미리보기만 지웁니다. DB 저장·확정 상태 변경·Coverage 재계산을 하지 않고,
  과거에 적용한 제외/방문/미방문 칸은 그대로 남습니다. (확정된 수동 설정을 전부 지우는 버튼은 없습니다.)
- **수동 상태 우선순위** — 한 칸은 셋 중 하나의 수동 상태만 가집니다.

  ```
  excluded  → Coverage 대상에서 제외 (가장 먼저)
  unvisited → 유효 셀, 방문 0회 (실제 GPS 기록은 지우지 않음)
  visited   → 유효 셀, 방문 max(1, 실제)
  (없음)    → 실제 GPS 방문 횟수
  ```

### Coverage 캐시 · 탭 전환

- 다른 탭에 갔다가 누적 지도로 돌아오면, 그사이 바뀐 게 없는 한 **다시 계산하지도 다시 그리지도 않습니다** —
  기존 지도와 Layer를 그대로 두고 `accumMap.invalidateSize()`와 버튼/안내 문구만 갱신합니다(`enterAccumView()`).
- 캐시는 두 층입니다.
  - **정적 Geometry**(날짜와 무관): 구역 polygon 안의 도로 칸, gap healing, 건물·아파트·주차장 제외.
    키 = 구역, 경계 polygon 해시, Cell 크기, 경계/지도 데이터 revision.
  - **동적 결과**(날짜별): 방문 횟수, 방문/미방문 판정, 수동 셀 반영. 키 = 구역, **정규화된 시작일·종료일**, 경계
    polygon 해시, 데이터 revision, 수동 셀 revision, Cell 크기, Coverage 설정 revision.
    그래서 "전체 기간"과 "2026-09-01 ~ 2026-09-05"는 서로 다른 캐시이고, 날짜를 바꾸면 방문 집계만 새로 하고
    Geometry는 재사용합니다. 이전에 본 날짜 범위로 돌아가면 캐시를 그대로 씁니다.
  - Coverage %·Cell 수·Depth 분포와 지도 색은 동적 결과로부터 계산하며, Depth·디버그 보기 전환은 다시 그리기만 합니다.
- **무효화(재계산) 조건**
  - 모든 구역: 주행기록 import, 날짜/전체 삭제, 백업 복원, 서버 동기화, Coverage 설정(`setSettings`) 변경
  - 해당 구역만: 수동 셀 "선택 적용", 구역 경계 추가·수정(꼭짓점 드래그)·삭제
  - 키가 달라져서 새로 계산: 선택 구역 변경, 날짜 필터 변경(방문 집계만 — Geometry 재사용, 같은 범위 재적용은 무시)
  - 날짜를 바꾸는 동안 이전 범위로 진행 중이던 계산은 `accumRenderToken`으로 버려져 새 결과를 덮지 않습니다.
  - 도로/건물 데이터를 못 받아 대체값(예전 캐시/빈 목록)으로 계산한 결과는 "임시"로만 두고, 다음에 탭으로
    들어올 때 다시 받아서 계산합니다.
- 저장소 쪽 변경은 `RouteDB.onChange()` 알림으로 전달되고(서버 동기화는 `sync.js`가 `RouteDB.notifyChange('sync')`),
  늦게 끝난 비동기 계산은 `accumRenderToken` 확인 후에만 지도에 그려서 최신 화면을 덮지 않습니다.

### 저장 형식 · 호환성

| | 위치 | 형식 |
|---|---|---|
| SQLite | `zones.manual_cells` (TEXT, JSON) | `{"excluded":[[lat,lng],...],"visited":[...],"unvisited":[...]}` |
| IndexedDB | `zones` 스토어 행의 `manualCells` | 같은 객체 |

- 칸은 gy/gx가 아니라 **칸 중심 위경도**로 저장하고, 매번 그 시점 격자로 다시 칸을 계산합니다.
- `getZoneManualCells()`는 두 저장소 모두 항상 세 배열을 돌려줍니다. `unvisited`가 없는 **구버전 데이터**
  (`excluded`/`visited`만)는 별도 DB 마이그레이션 없이 `unvisited: []`로 읽힙니다. 깨진 값은 빈 목록으로 처리합니다.
- **백업**: `zones[].manualCells`로 함께 저장됩니다(SQLite `listZones()`도 이제 포함).
- **복원**: 병합/전체 교체 모두 수동 셀은 **칸 단위 병합** — 백업에 있는 칸은 백업 상태로, 백업에 없는 지금 칸은
  유지. `manualCells`가 없는 옛 백업은 수동 셀을 건드리지 않습니다.
- **서버 동기화**: `server.js`가 구역을 이름 기준으로 병합할 때 `manualCells`도 칸 단위 병합하고, `manualCells`를
  보내지 않는 구버전 기기가 기존 값을 지우지 못하게 합니다. 받아온 쪽은 위의 복원 규칙으로 저장합니다.

## 실행 · 빌드 · 테스트

Node.js가 없으면 `tools/setup-node.ps1`이 프로젝트 안 `tooling/`에 포터블 Node를 받습니다.

```powershell
powershell -ExecutionPolicy Bypass -File tools\setup-node.ps1
$env:Path = "$PWD\tooling\node-v24.19.0-win-x64;" + $env:Path

npm install
npm start          # 데스크톱 앱 개발 실행 (SQLite)
npm test           # 단위/통합 테스트 (아래 표의 npm test 항목 전부)
npm run pack       # release/win-unpacked 만 생성
npm run dist       # release/ 에 설치 파일 + 포터블 생성
node server.js     # 브라우저 모드(IndexedDB) + 서버 동기화 서버 → http://localhost:8080/src/index.html
npm run test:browser-capture   # 브라우저 모드 지도 캡처 E2E (Electron 창을 브라우저로 사용, 인터넷 필요)
```

브라우저 모드는 저장소 루트의 **`브라우저로 열기.bat` 을 더블클릭**해도 됩니다 — 서버를 띄우고 포트가 열릴 때까지
기다렸다가 브라우저를 엽니다. 서버가 이미 떠 있으면 브라우저만 엽니다. 서버 설정(`HOST` 등)은 바꾸지 않고
접속 주소만 `127.0.0.1` 을 씁니다.

> `src\index.html` 을 탐색기에서 더블클릭해 `file://` 로 열면 서버를 거치지 않으므로 타일 프록시·서버 동기화를 쓰지
> 못하고, 타일을 브라우저가 OSM 에서 직접 받습니다 — 그 브라우저 상태에 따라 차단될 수 있습니다. 브라우저 모드는
> 런처로 여세요. (예전 README 에 "file:// 은 Referer 가 없어 원리적으로 차단된다"고 적었던 것은 curl 로 헤더를 흉내 낸
> 측정에서 나온 틀린 결론이었습니다 — 실제 Edge 는 file:// 에서도 통과했습니다.)

## 알려진 이슈

- **교통 시간대·조도 조건 — 아직 없는 것**: 공휴일은 평일로 셉니다(요일 구분은 토·일만 주말). 날씨는 파일 원본 문자열
  그대로라 표기가 다르면(`비`/`강우`) 다른 값입니다. 시간대는 `Asia/Seoul` 고정 오프셋만 지원합니다. 교통 시간대는 8개
  구간의 시각만 바꿀 수 있고 구간 추가·삭제·이름 변경은 없습니다. 요일·교통·조도·날씨를 골라 보는 복합 필터 화면과
  추천 기능은 없고 집계 API만 있습니다. 누적 지도(밀도·Coverage)에는 조건 필터가 없습니다(데이터 상태 필터는 있습니다).
- **Import 이슈 — 아직 없는 것**: 이슈는 파일 단위로만 붙습니다(레코드 하나만 이슈로 표시할 수 없고, 한 파일에
  메모도 하나입니다). 이슈 종류/태그 분류, 담당자, 처리 이력(누가 언제 확인 완료로 바꿨는지)은 없습니다.
  회색 표시는 밀도 지도(원)와 통계 막대에만 있습니다 — Coverage Map 의 칸 색은 방문/미방문 판정을 나타내므로
  이슈 색을 겹치지 않았습니다(대신 '이슈 없음'으로 보면 그 기록을 뺀 Coverage 가 다시 계산됩니다).
  데이터 상태 필터로 하루가 일부만 남으면 주행 시간(첫 기록~마지막 기록)은 합계에서 빠집니다 —
  Import 출처별로 나눌 수 없는 값이라 그렇습니다(수집 시간·기록 수는 정확히 나뉩니다).
- **추천 주행 — 아직 없는 것**: LLM 은 연결돼 있지 않습니다(구조화 payload 와 지시문만 준비). Coverage 는 누적 지도에서
  한 번 계산해야 추천 점수에 들어가고, 조건별(요일·시간대·조도) Coverage 는 계산하지 않습니다. 실제 Edge Case 이벤트 로그가
  없어 모든 예상 Edge Case 는 조건 기반 추정입니다. 목표 기본값(피크 240분·4회 등)은 데이터가 아니라 정책 기본값입니다.
  공휴일은 평일로 셉니다. 추천 상태(기간 제외·완료 표시)는 기기마다 따로이며 백업·동기화에 포함되지 않습니다.
- **분류 설정도 서버 동기화로 퍼집니다.** `server.js`가 설정을 "나중에 올린 값 우선"으로 합치므로, 한 기기에서 교통
  시간대를 바꾸고 동기화하면 다른 기기가 다음 동기화 때 그 설정을 받아 재분류합니다.

- **`release/win-unpacked`의 패키지 앱은 3.1.1**이라 날짜 필터·지도 캡처가 들어 있지 않습니다(그 `app.asar`에는
  날짜 입력칸과 `fromDate` 조건이 없음). 3.1.2 설치 파일은 이번에 빌드하지 않았습니다 — `npm run dist`가 필요합니다.
- 데스크톱 앱의 지도 캡처는 창보다 큰 지도면 보이는 부분만 저장됩니다(브라우저 모드는 지도 전체).
  브라우저 모드 캡처는 배경 타일 서버의 CORS 허용(현재 OSM은 허용)에 기대고, Safari에서는 타일 흑백 필터가 빠집니다.
- **지역별 Coverage 요약 패널이 비어 있습니다.** `index.html`에 `#coverage-summary` 자리가 있고 E2E도 이 요약을
  확인하지만, 현재 코드에는 이 영역을 채우는 함수가 없습니다(선택한 한 구역의 상세 패널 `#coverage-detail`만 동작).
  그래서 E2E의 "요약에 강남 Coverage %가 표시된다" 1건은 이번 변경 전 코드에서도 실패합니다.
- **건물 데이터(Overpass) 대기가 길 수 있습니다.** 미러 4곳을 순서대로 각 15초 제한으로 시도해서, 미러가 응답하지
  않으면 첫 Coverage 계산이 수십 초 걸립니다(이번 점검 중 `overpass-api.de`는 HTTP 406을 반환). 이 경고가 E2E의
  "화면 콘솔 에러"로 집계돼 E2E 종료 코드가 1이 됩니다.
- **동기화로는 "지우기"가 전파되지 않습니다.** 수동 셀·구역 경계는 병합만 하므로, 한 기기에서 해제한 칸이 다른
  기기/서버에 남아 있으면 다음 동기화 때 다시 돌아옵니다.
- `tools/e2e.ps1`에 다른 PC의 경로(`c:\Users\User\Downloads\...`)가 하드코딩돼 있습니다.
- `release/`, `node_modules/`, `tooling/`이 `.gitignore`에 있어도 이미 Git에 추적되고 있고, `주행기록/`·`백업/`의
  실제 GPS 기록도 커밋돼 있습니다(`.gitignore`에서 주석 처리됨). 정리 방법은 아래 보안 주의사항 참고.

## 서버 동기화 보안 주의사항

`server.js`는 **신뢰할 수 있는 내부망 전용** 도구로 만들어져 있습니다. 현재 동작:

- 기본 `HOST`가 `0.0.0.0`이라 같은 네트워크의 모든 기기에서 접속됩니다.
- `GET /api/route-data`는 **인증이 없습니다** — 서버에 모인 모든 GPS 기록·구역·설정을 누구나 받을 수 있습니다.
- `ROUTE_VIEWER_WRITE_TOKEN`을 설정하지 않으면 **누구나 PUT으로 데이터를 넣을 수 있고**, 그 데이터는 동기화하는
  모든 데스크톱 앱에 병합됩니다.
- 정적 파일 핸들러가 프로젝트 폴더 전체를 내려주므로, 이 폴더에서 서버를 띄우면 `/.git/…`, `/백업/*.json`,
  `/주행기록/*.xlsx` 같은 파일도 그대로 다운로드됩니다.
- 자동 업데이트는 입력한 서버 주소(`<주소>/updates`, 보통 `http://`)에서 받으며, 설치 파일에 코드 서명이 없습니다
  (`signAndEditExecutable: false`). 같은 네트워크의 공격자가 업데이트 파일을 바꿔치기할 수 있습니다.

권장: `HOST=127.0.0.1` 또는 방화벽으로 접근 제한, `ROUTE_VIEWER_WRITE_TOKEN` 필수 설정, 가능하면 HTTPS 리버스
프록시 뒤에서 운영하고, 개인 데이터가 없는 별도 폴더에서 서버를 실행하세요.
