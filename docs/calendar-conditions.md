## 달력 — 전체 데이터 수집 현황

달력 탭 맨 위에 DB에 저장된 **전체 기간** 데이터의 누적 현황을 표로 보여줍니다(보고 있는 달·선택한 날짜와 무관).

| 구분 | 목표 Clip 수 | 목표 시간(분) | 주행 시간(분) | 수집 시간(분) | 진행률(%) |
|---|---:|---:|---:|---:|---:|
| KPI | 8,000 | 4,000 | 자동 계산 | 자동 계산 | 수집 시간 ÷ 4,000 × 100 |
| 제안 | 20,000 | 10,000 | 자동 계산 | 자동 계산 | 수집 시간 ÷ 10,000 × 100 |

- **두 가지 시간을 따로 보여줍니다.**
  - **주행 시간** — 날짜·차량별 첫 기록부터 마지막 기록까지(점심·휴식 등 GPS가 끊긴 시간 포함). "마지막 시각 − 첫 시각"
    단순 계산과 같은 값입니다(`CollectionStats.spanDurationSec`).
  - **수집 시간** — 그중 GPS가 실제로 기록된 시간(아래 규칙). **진행률은 수집 시간 기준**이며, 진행률 아래에 주행 시간
    기준 진행률을 참고로 작게 적습니다(예: "주행 기준 142.7%").

- **목표값**은 `src/js/collection-stats.js`의 `COLLECTION_TARGETS` 한 곳에서 관리합니다(표의 행도 이 목록으로 그림).
  목표 Clip 수는 현재 목표값만 표시하고, 진행률은 **수집 시간 기준**입니다.
- **수집 시간(유효 수집 시간)** 계산 규칙 — SQLite와 IndexedDB가 같은 함수(`CollectionStats.validDurationSec`)를 씁니다.
  1. 날짜별 · 차량별로 기록을 나눕니다.
  2. 차량마다 시각 순으로 정렬하고(같은 시각 기록은 하나로 봄) 연속한 두 기록의 간격을 구합니다.
  3. 간격이 0초 초과 **90초 이하**면 더하고, **90초보다 긴 간격은 GPS 공백으로 보고 뺍니다**
     (기존 품질 검사의 "GPS 공백" 기준과 같은 값). 오전 1시간 + 오후 1시간 = 2시간(마지막−처음 = 9시간이 아님).
  4. 차량별 합계를 더합니다 — 여러 차량이 같은 시간대에 수집하면 각각 따로 셉니다.
  5. 모든 날짜를 더해 초 → 분으로 바꿉니다. 표의 수집 시간은 반올림한 정수 분, 진행률은 초 단위 값으로 계산해
     소수 첫째 자리까지 표시합니다(예: 1,234분 → KPI 30.9%, 제안 12.3%).
- **중복 제외**: import 때 `date|time|vehicle|lat|lng`로 중복 제거돼 DB에 실제로 남은 기록만 씁니다. 같은 파일 재등록,
  동일 GPS 레코드, 삭제된 날짜는 들어가지 않고, 같은 차량·같은 시간대의 겹친 세션은 시각을 합쳐서 한 번만 셉니다.
  (차량 이름이 파일마다 다르게 적혀 있으면 — 예: "토레스 3호"/"토레스 3호차" — 다른 차량으로 셉니다.)
- **목표 초과**: 진행률 숫자는 100%로 자르지 않고 그대로(예: 4,500분 → 112.5%), 진행 막대 너비만 최대 100%입니다.
  데이터가 없으면 수집 시간 `0`, 진행률 `0.0%`입니다. 표 오른쪽 위에 DB의 가장 최신 기록 날짜를 "최근 데이터"로 표시합니다.
- **저장·성능**: 날짜별 유효 수집 시간은 import·삭제·백업 복원·서버 동기화 때 만들어지는 날짜 요약에
  `collectionSec`(수집)·`driveSpanSec`(주행)로 저장되고, 달력은 날짜 요약만 더합니다(원본 GPS 기록을 다시 읽지 않음).
  이 값이 없는 예전 DB는 앱을 처음 켤 때 날짜 요약을 한 번 다시 만듭니다(`summary_version` 4 — 4에서 교통 시간대·조도
  조건 칸이 추가됨, 아래 "교통 시간대 · 조도 조건" 참고).
- **자동 갱신**: 앱 시작, 파일 import, 날짜/전체 삭제, 백업 복원, 서버 동기화 뒤 날짜 요약을 다시 읽을 때
  (`refreshDateIndex`) 한 번만 다시 합산합니다. 월 이동·날짜 선택으로는 다시 계산하지 않습니다.
- **달력 칸**마다 그 날짜의 `수집 N분 · 주행 N분`을, **일자 요약**(날짜 클릭)에는 주행 시간과 수집 시간을 따로
  보여줍니다(수집 시간 옆에 "공백 N분 제외").
- 참고: 이 저장소의 `주행기록/` 28개 파일(14일)을 넣으면 **주행 5,706분 · 수집 3,093분**입니다
  (진행률 KPI 77.3%·제안 30.9%, 주행 기준 참고값 KPI 142.7%·제안 57.1%). 빠진 2,613분의 대부분은 하루 1~3시간씩
  기록이 통째로 없는 구간입니다 — 30분 넘는 공백 28개가 1,919분, 10~30분 공백 25개가 478분, 90초~10분 공백은
  216분뿐입니다(주행 중 기록 간격은 대부분 10초 이하).

## 교통 시간대 · 조도 조건

### 왜 두 축으로 나눴나

예전에는 "시간대"가 파일의 `시간대` 열(nav-app이 넣은 `주간`/`일몰`) 하나뿐이었습니다. 여기에 출근·퇴근 같은 피크타임을
섞으면 `퇴근 일몰` 같은 값이 생겨 "퇴근 피크인데 아직 밝은 날"과 "퇴근 피크이면서 해가 지는 날"을 구분할 수 없습니다.
교통 흐름과 빛의 상태는 서로 독립이라 **서로 다른 필드**로 둡니다.

| 축 | 필드 | 기준 | 값(내부 식별자 → 화면) |
|---|---|---|---|
| 교통 시간대 | `trafficPeriod` | 고정 시각 구간(설정에서 수정) | `late_night` 심야 · `early_morning` 이른 아침 · `morning_peak` 출근 피크 · `morning_offpeak` 오전 비피크 · `lunch_peak` 점심 피크 · `afternoon_offpeak` 오후 비피크 · `evening_peak` 퇴근 피크 · `night` 야간 · `unknown` 미분류 |
| 조도 조건 | `lightCondition` | 날짜·GPS로 계산한 일출·일몰 | `sunrise` 일출 전후 · `daylight` 주간 · `sunset` 일몰 전후 · `night` 야간 · `unknown` 미분류 |
| 요일 | `weekdayType` | 날짜 | `weekday` 평일 · `weekend` 주말 · `unknown` 미분류 |
| 날씨 | `weather` | 파일 `날씨` 열 원본 | 원본 문자열 그대로(`맑음`/`흐림`/`비`, 없으면 빈 값 = "정보 없음") |

- 저장·비교는 항상 **내부 식별자**로 하고 화면 이름은 `src/js/time-conditions.js`의 라벨 표에서만 붙입니다 — 이름을 바꿔도
  기존 데이터가 깨지지 않습니다.
- 교통 시간대의 `야간`(20:00~24:00 고정 구간)과 조도 조건의 `야간`(해가 없는 시간)은 이름만 같고 다른 값입니다
  (예: 6월 21일 20:05 → 교통 `야간` + 조도 `일몰 전후`). 하나의 변수·컬럼으로 합치지 않습니다.
- 파일의 `시간대` 열(`timeOfDay`)은 **삭제하거나 의미를 바꾸지 않고** 원본 그대로 보존합니다. 통계 탭에는
  "파일 원본 시간대" 카드로 남아 있습니다. 참고로 이 저장소의 실제 기록에서 원본 `일몰`(17시대 4,763건)은 실제 일몰
  (18:40~19:28)보다 1시간 이상 일러서 계산된 조도 조건은 `주간`입니다 — 두 값이 다른 게 정상입니다.

### 교통 시간대 — 기본값과 경계 규칙

| 교통 시간대 | 시작 | 종료 |
|---|---:|---:|
| 심야 | 00:00 | 05:00 |
| 이른 아침 | 05:00 | 07:00 |
| 출근 피크 | 07:00 | 10:00 |
| 오전 비피크 | 10:00 | 11:30 |
| 점심 피크 | 11:30 | 13:30 |
| 오후 비피크 | 13:30 | 17:00 |
| 퇴근 피크 | 17:00 | 20:00 |
| 야간 | 20:00 | 24:00 |

- **`시작 <= 시각 < 종료`** — 초 단위까지 봅니다(`04:59:59` 심야, `05:00:00` 이른 아침, `23:59:59` 야간).
- `24:00`은 다음 날 `00:00`과 같은 경계입니다. 설정의 종료 `00:00`은 `24:00`으로 저장되고, 기록 시각 `24:00:00`은 심야입니다.
- 종료를 시작보다 이르게 쓰면 자정을 넘는 구간입니다(예: 심야 `22:00~05:00`).
- 시각이 없거나 파싱할 수 없는 기록(`25:00:00`, 문자 등)은 임의의 구간에 넣지 않고 `unknown`(미분류)입니다.
- 판정은 이름·배열 순서가 아니라 **저장된 시작·종료 시각**으로만 합니다.

### 설정 탭에서 수정하기

[설정] → **교통 시간대**에서 각 구간의 시작·종료를 `HH:mm`으로 고치고 **저장**, 기본값으로 돌리려면 **기본값 복원**
(바로 저장·재분류). 입력하는 동안 검증 결과를 보여주고, 아래 중 하나라도 있으면 저장 버튼이 꺼지고 이유가 표시됩니다.

- 형식 오류(`7:00`, `07:60`, 시작 `24:00`) · 시작=종료(길이 0) · 빠진/중복/알 수 없는 시간대
- **겹침** — 예: `출근 피크(07:00~10:00)와(과) 오전 비피크(09:30~11:30)이(가) 09:30~10:00에서 겹쳐요.`
- **공백** — 예: `11:00~11:30이(가) 어느 교통 시간대에도 속하지 않아요(공백).`
- 하루 1,440분이 정확히 한 번씩 덮이는지 분 단위로 확인합니다.

같은 검증(`TimeConditions.validateTrafficPeriods`)을 저장소(SQLite `setSettings` / IndexedDB `setSettings`)가 저장 직전에
다시 하므로 화면을 거치지 않은 잘못된 설정도 저장되지 않습니다. 설정 구조(`app_settings`, 두 저장소 동일):

```js
trafficPeriods: [{ id: 'late_night', label: '심야', start: '00:00', end: '05:00' }, …],  // 시작 시각 순으로 저장
sunriseWindowMinutes: 30,
sunsetWindowMinutes: 30,
```

저장값이 없거나(구버전) 깨졌으면 기본값으로 판정합니다. 백업·서버 동기화로 들어온 잘못된 분류 설정은 그 값만 무시하고
지금 설정을 유지합니다.

### 조도 조건 — 일출·일몰 계산

- **계산 방식**: 외부 API 없이 로컬 계산 — NOAA Solar Calculator와 같은 Meeus 천문 알고리즘(태양 적위·균시차를 일출·일몰
  시각에서 반복 보정, 천정각 90.833° = 대기 굴절·태양 반지름 반영). 입력은 **주행 날짜 · GPS 위도 · GPS 경도 · 시간대**.
- **정확도**: 미 해군천문대(USNO) 공개값과 강남(37.4979, 127.0276) 기준 2026년 춘분·하지·8/12·9/15·동지 모두 **1분 이내**
  (실측 오차 최대 0.5분, `tests/time-conditions-test.js`에 기준값·출처 URL 포함).
- **캐시**: `날짜 + 위도·경도(0.01° ≈ 1.1km 반올림)`로 계산 결과를 재사용합니다. 반올림한 좌표로 계산하므로 캐시와
  무관하게 항상 같은 값입니다. 실제 기록 약 20만 번 조회에 계산 335번이었습니다.
- **범위(기본 ±30분, 경계 포함)**: 일출 ± `sunriseWindowMinutes` → 일출 전후 · 일몰 ± `sunsetWindowMinutes` → 일몰 전후 ·
  그 사이 → 주간 · 나머지 → 야간. 겹치면 일출 전후가 우선입니다. [설정] → **조도 조건**에서 0~180분으로 바꿀 수 있습니다.
- 백야/극야(일출·일몰이 없는 날)는 각각 주간/야간입니다.
- **날짜 없음**(`날짜미상`, 없는 날짜) · **GPS 없음**(빈 값·NaN·범위 밖·`0,0`) · 시각 파싱 실패 → `unknown`(미분류).
  날짜만 없으면 교통 시간대는 시각으로 정해지고 조도·요일만 미분류입니다.

### 한국 현지 시간 처리

- 기록의 `date`(`YYYY-MM-DD`)·`time`(`HH:MM:SS`)은 이미 한국 현지 벽시계 값입니다. 분류 코드는 `new Date('…T…')`처럼
  실행 환경 시간대로 해석되는 변환을 쓰지 않고 문자열을 숫자로 쪼개 계산합니다(`Date` 객체 입력은 받지 않음).
- 일출·일몰은 UTC로 계산한 뒤 **고정 오프셋 `Asia/Seoul` = +09:00**(서머타임 없음)을 더합니다.
- 테스트가 같은 계산을 `TZ=UTC` · `TZ=America/Los_Angeles` · `TZ=Asia/Seoul` 자식 프로세스로 돌려 66건 결과가 모두
  같은지 확인합니다(각 프로세스의 실제 시간대 오프셋 0/420/-540도 확인).

### 저장 방식 · 재분류

**선택: 파생값은 기록에 저장하지 않고, 날짜 요약에만 "조건 칸 + 분류 서명"으로 캐시한다.**

- 교통 시간대·조도·요일은 원본(시각·날짜·GPS)에서 다시 계산할 수 있는 파생값입니다. `driving_records`(SQLite)·
  `records`(IndexedDB)에는 컬럼/필드를 추가하지 않았고, 기록을 읽을 때(`getRecordsByDate`) 지금 설정으로 계산해 붙입니다.
- 날짜 요약(`date_summaries.summary_json` / `summaries`)에 **조건 칸 `conditionCells`**를 저장합니다 — 칸 하나 =
  `zone × vehicle × weekdayType × trafficPeriod × lightCondition × weather` 조합이고, 칸마다 `recordCount` ·
  `collectionSec`(유효 수집 시간) · `firstTime` · `lastTime`을 가집니다(실제 기록 기준 날짜당 수십 칸).
- 요약마다 **`classificationSignature`**(판정 규칙 버전 `CLASSIFICATION_VERSION` + 교통 시간대 + 일출·일몰 범위 + 시간대)를
  같이 적습니다. 서명이 지금 설정과 다른 날짜가 "재분류 필요"입니다.
- **이 방식을 고른 이유**: ① 달력·통계는 이미 날짜 요약만 읽는 구조라, 조회할 때마다 원본 10만 건을 다시 분류(방식 A)하지
  않아도 됩니다. ② 기록마다 값을 저장(방식 B)하면 설정을 바꿀 때 원본 테이블을 대량 수정해야 하고, 백업·동기화에 옛
  분류값이 섞여 들어갑니다. 요약만 다시 만들면 원본은 절대 바뀌지 않습니다. ③ 실측(이 저장소 실제 기록 102,632건·16일)
  전체 요약 재생성이 약 0.6초라 설정 변경 때 다시 만들어도 부담이 없습니다.
- **재분류 흐름**: 설정 저장(검증 통과) → `reclassifySummaries()`가 서명이 다른 날짜만 하나씩 다시 만듭니다.
  - **진행 표시**: 설정 탭 하단 `재분류 중… n / m일`(`getClassificationStatus()`의 `progress`를 300ms마다 조회).
    SQLite는 날짜 사이마다 이벤트 루프를 비워서 도는 중에도 진행률 요청에 답합니다.
  - **중복 실행 방지**: 화면 플래그 + 저장소가 이미 돌고 있는 작업(같은 Promise)을 돌려줍니다. 버튼·입력도 잠급니다.
  - **실패 시 보존**: 날짜 요약 한 건을 한 문장(SQLite UPSERT)/한 번의 `put`(IndexedDB)으로 통째로 바꾸므로, 중간에 실패해도
    각 날짜는 예전 요약이거나 새 요약입니다. 원본 기록은 건드리지 않습니다. 남은 날짜는 "지금 재분류"로 이어서 처리됩니다.
  - **종료 후 다시 열기**: 앱 시작 시(SQLite 생성자 `_migrateSummaries` / IndexedDB `init`) 서명이 다른 날짜를 이어서
    재분류합니다.
  - **캐시 무효화**: 완료 후 `refreshDateIndex()`로 달력·일자 요약 캐시를 다시 읽고, 통계는 탭을 열 때 날짜 요약으로 다시
    집계합니다. 재분류 전이면 통계·일자 요약에 "아직 다시 분류하지 않은 날짜" 경고가 뜹니다. 분류 설정만 바꾼 저장은
    누적 지도 Coverage 캐시를 무효화하지 않습니다(무관). 추천 기능·추천 캐시는 아직 없습니다.
- 백업 복원·서버 동기화가 분류 설정을 바꾸면 복원 끝에 같은 재분류를 동기로 실행합니다.

### 구버전 데이터 호환

- **기존 Excel**: 새 열이 필요 없습니다. `시간대`·`날씨` 열이 없는 옛 파일도 Import 되고 시각·GPS로 분류됩니다.
- **기존 SQLite DB / IndexedDB**: 스키마 변경이 없고, 요약 형식 버전(`summary_version` 3 → 4)이 달라 앱을 처음 열 때 날짜
  요약을 한 번 다시 만듭니다(별도 초기화 불필요, 원본 기록·해시 그대로).
- **기존 백업**: 분류 필드·분류 설정이 없어도 복원됩니다. 백업 안에 분류값이 들어 있어도 믿지 않고 다시 계산합니다.
- **중복 판정**: 키(`date|time|vehicle|lat|lng`)와 충돌 비교 필드(`place/road/weather/timeOfDay/traffic/speed`)는 그대로입니다.
  분류는 어느 쪽에도 들어가지 않아, 설정을 바꾸고 같은 파일을 다시 넣어도 새 레코드는 0건입니다.

### 달력 · 통계 · 재생 화면

- **일자 요약**(달력에서 날짜 클릭): `교통 시간대`와 `조도 조건`을 각각 막대 + `N분 · M개`로, 아래에 **조건 조합**(수집 시간
  많은 순 6개)을 축별 배지 `[요일 평일] [교통 퇴근 피크] [조도 일몰 전후] [날씨 비]`로 보여줍니다. 분 단위는 기존 유효 수집
  시간 규칙(차량별 90초 넘는 GPS 공백 제외)이라 두 축 각각의 합이 그날 "수집 시간"과 같습니다.
- **통계 탭**(지역별/차량별 필터 그대로 적용): 교통 시간대 · 조도 조건 · 평일/주말 카드(수집 분 · 기록 수), 분류 기준 안내,
  **구역별(지역 모드) 또는 차량별(차량 모드) × 교통 시간대 / × 조도 조건** 수집 분 표.
- **GPS 리플레이**: 재생 중인 지점의 `교통 · 조도 · 요일 · 날씨`를 배지로 따로 표시합니다.

### 집계 API (향후 추천 입력)

`ConditionStats.aggregate(summaries, { filter, groupBy, signature })` — `summaries`는 `RouteDB.listDateSummaries()` 결과.

- `filter`: `zone` · `vehicle` · `vehicleLike` · `date` · `fromDate` · `toDate` · `weekdayType` · `trafficPeriod` ·
  `lightCondition` · `weather` (조건 축은 값 하나 또는 배열)
- `groupBy`: `zone` · `vehicle` · `weekdayType` · `trafficPeriod` · `lightCondition` · `weather` 중 원하는 조합
- 결과 행: `{ ...묶은 축, recordCount, collectionSec, collectionMinutes, visitCount, lastVisitedAt }` +
  `totals` · `staleDates`(서명이 다른 날짜 수) · `dateCount`. `visitCount` = 그 조합에 기록이 있는 (날짜, 차량) 수,
  `lastVisitedAt` = 마지막 기록 시각(`2026-09-16T18:50:00+09:00` 형식).
- `ConditionStats.fillMissing(rows, { zone: [...], lightCondition: [...] })`로 기록이 없는 조합을 0으로 채워
  "일몰 전후 데이터가 없는 구역", "출근 피크에 가장 적게 주행한 구역"을 구합니다(테스트에 예시 질문 포함).

`groupBy: ['zone','weekdayType','trafficPeriod','lightCondition','weather']` 결과 한 줄 — `tests/time-conditions-test.js`
합성 데이터(9/15 1호·9/16 2호, 강남, 비)의 실제 출력:

```js
{ zone: '강남', weekdayType: 'weekday', trafficPeriod: 'evening_peak', lightCondition: 'sunset', weather: '비',
  recordCount: 102, collectionSec: 3000, collectionMinutes: 50, visitCount: 2, lastVisitedAt: '2026-09-16T18:50:00+09:00' }
```

이 집계 API 를 그대로 쓰는 것이 아래 **추천 주행** 탭입니다(구역·요일·교통 시간대·조도·날씨 조합의 부족도 계산).
