## 추천 주행

### 목적

"다음에 어디를, 언제, 몇 번 더 달려야 하는가"를 지금까지 모인 데이터에서 **근거를 가지고** 계산합니다.
임의의 장소를 고르지 않고, 구역·요일·교통 시간대·조도·날씨별 수집량과 Coverage 를 비교해 부족한 조합을 찾습니다.

### 구조 — 순위와 수치는 통계 엔진이 정한다

```
주행기록 DB(날짜 요약의 조건 칸)
→ buildRecommendationFeatures()   구역×요일×교통 시간대×조도×날씨 집계 + 데이터 품질·차량·날씨 목록
→ 후보 생성                        활성 구역 × 평일/주말 × 교통 시간대 × (그 시간대에 실제로 생기는) 조도
→ calculateDeficitScores()        하위 점수 6개(각 0~100)
→ calculateRecommendationScore()  가중합(0~100) · 데이터 없는 항목 제외 후 재정규화
→ estimateCollectionNeed()        권장 시간 범위 · 추가 방문 횟수 · 추가 수집 시간
→ inferEdgeCaseHints()            조건 → 관찰 가능성이 높은 상황(규칙 표·근거 추적)
→ calculateConfidence()           점수와 별개인 "판단에 쓸 데이터가 충분한가"
→ generateRecommendationReason()  템플릿 문장 + 사실 목록(reasonFacts)
→ toLlmPayload() / buildLlmContext()  향후 LLM 에 넘길 구조화 사실
```

- 계산은 전부 `src/js/recommendation.js`(순수 함수, UMD)에 있고 화면(`src/js/recommend-view.js`)은 읽고 그리기만 합니다.
- **LLM 은 이번 구현에 연결돼 있지 않습니다.** 나중에 붙여도 순위·점수·Edge Case 를 만들지 않고 설명·비교만 하도록
  구조화된 사실과 지시문(`buildLlmContext().instructions`)만 넘깁니다.

### 분석 단위와 입력 데이터

분석 단위는 **구역 × 요일 유형 × 교통 시간대 × 조도 조건 × 날씨**입니다. 날짜 요약의 조건 칸(conditionCells)을 더해
만들기 때문에 원본 GPS 기록을 다시 읽지 않습니다(실측: 강남·판교·시흥 활성 구역, 16일·102,632건 기준 후보 66개 생성에 약 45ms).

| 쓰는 데이터 | 출처 |
|---|---|
| 구역·요일·교통 시간대·조도·날씨별 기록 수 · 유효 수집 시간 · 방문 횟수 · 고유 수집일 · 마지막 방문 | 날짜 요약의 조건 칸 |
| 차량별 수집 시간(편중) · 평균/저속/정차 비율 | 조건 칸(차량속도 통계) |
| GPS 공백·점프(품질 경고) · 수집/주행 시간 · KPI·제안 목표 대비 부족량 | 날짜 요약 |
| 구역 Coverage %·유효/미방문 Cell | 누적 지도가 계산해 저장한 **Coverage 스냅샷** |
| 일출·일몰 시각 | 구역 좌표 + 추천 기준 날짜로 계산(time-conditions.js) |

| 쓰지 않는 데이터 | 이유 |
|---|---|
| 교통밀도 열 | 실제 파일에서 값이 대부분 `(미측정)` |
| 도로 유형·어린이보호구역·아파트 인접·교차로 | 기록에 없음(도로종류는 전부 `도심`) — 해당 Edge Case 규칙도 적용하지 않음 |
| 미래 날씨 | 날씨 예보와 연결돼 있지 않음 — "우천 시 우선" 같은 조건 표현까지만 |
| 실제 Edge Case 이벤트(검출·급정거·Cut-in 등) | 아직 수집 항목이 아님 |

`unknown`(시각·GPS·구역을 못 읽은 기록)은 후보 조합으로 만들지 않고, 그 비율만큼 신뢰도를 낮춥니다.

### 추천 점수

```js
recommendationScore =
  timePeriodDeficit * 0.30 + coverageDeficit * 0.25 + lightConditionDeficit * 0.15 +
  weatherDiversityDeficit * 0.15 + staleness * 0.10 + vehicleImbalance * 0.05;
```

| 항목 | 의미 | 계산 |
|---|---|---|
| 시간대 부족도 | 그 구역·요일의 교통 시간대 전체가 목표에 얼마나 못 미치는가 | `100 × (1 − (수집 시간 달성률×0.5 + 방문 횟수 달성률×0.3 + 고유 수집일 달성률×0.2))` |
| Coverage 부족도 | 구역의 도로 칸을 얼마나 못 밟았는가 | `(목표 Coverage − 현재)/목표 × 100` |
| 조도 조건 부족도 | 그 시간대 안의 조도 조건이 부족한가 | 시간대 목표 × (그날 그 시간대에서 해당 조도가 차지하는 비율)로 목표를 나눈 뒤 같은 부족도 식 |
| 날씨 다양성 부족도 | 기록된 날씨 종류에 고르게 모였는가 | 조건 목표를 기록된 날씨 종류 수로 균등 배분해 비교 |
| 최근 미방문 기간 | 마지막 방문 이후 얼마나 지났는가 | `경과 일수 / 기준 일수 × 100`(방문 기록이 없으면 100) |
| 차량 편중도 | 한 차량에 쏠렸는가 | `(최다 차량 비율 − 균등 비율)/(100% − 균등 비율) × 100` |

- 기록 수(GPS 포인트 수)만으로 판단하지 않습니다 — 하루에 한 번 오래 모은 것을 다양하다고 보지 않으려고 **수집 시간 ·
  방문 횟수 · 고유 수집일**을 함께 봅니다.
- **데이터가 없는 항목은 점수에서 빼고**(예: Coverage 계산값 없음, 날씨 기록 없음, 차량 1대) 남은 가중치를 다시 100%로
  나눕니다. 어떤 항목이 왜 빠졌는지는 근거 상세와 카드의 "누락"에 적습니다.
- 목표가 설정되지 않은 시간대는 **같은 구역·같은 요일 유형의 다른 시간대 중앙값**을 비교 기준으로 쓰고, 그 기준을 화면에 적습니다.
- 우선순위: 80~100 매우 높음 · 60~79 높음 · 40~59 보통 · 0~39 낮음.

### 추천 점수 ≠ 신뢰도

- **추천 점수**는 "얼마나 먼저 모아야 하는가", **신뢰도**는 "이 판단에 쓸 데이터가 충분한가"입니다. 따로 계산합니다.
- 높음: 시각·GPS·구역 판정 비율이 높고 수집 기간·비교 조건·Coverage 가 모두 있음
- 보통: 일부 필드 누락, 수집일이 적음(7일 미만), 비교 대상이 적음, Coverage 계산값 없음/임시값, 구역 위치 없음
- 낮음: 시각·GPS·구역을 못 읽은 기록이 30% 초과, 수집일 2일 미만, 품질 경고가 기록 1,000건당 100건 초과
- 낮은 신뢰도 추천도 이유와 함께 표시하며, 설정에서 숨길 수 있습니다.

### 권장 시간 · 횟수 · 수집 시간

- **권장 시간 범위** = 교통 시간대 구간 ∩ 그 조도 구간(추천 기준 날짜 + 구역 좌표로 계산한 일출·일몰 ±설정 분). 5분 단위로
  안쪽 정렬합니다. 일출·일몰 시각은 하드코딩하지 않고 "다음 평일/주말" 날짜로 계산하며, 그 날짜와 일출·일몰 시각을 함께 보여줍니다.
- **추가 방문 횟수** = `max(목표 방문 − 현재 방문, ⌈부족 수집 시간 ÷ 회당 수집 가능 시간⌉)`.
  회당 수집 가능 시간 = 권장 시간 범위 × **수집 효율**(전체 수집 시간 ÷ 주행 시간, 데이터에서 계산).
- 한 번에 너무 많아지면 `추천당 최대 권장 횟수`(기본 3회)로 자르고 "전체 필요 N회 중 이번 M회"로 단계를 알려줍니다.
- 날씨는 예측하지 않습니다 — "날씨가 '비'인 날에 우선 수집" 같은 조건 표현만 씁니다.

### 예상 Edge Case — 가능성일 뿐

카드마다 다음 고지를 함께 보여줍니다: *"예상 Edge Case는 현재 시간대·도로 환경·날씨 조건을 기반으로 한 가능성 추정이며,
실제 발생을 보장하지 않습니다."* 근거 데이터가 없는 규칙은 적용하지 않고, 적용/미적용 규칙과 근거를 근거 상세에 남깁니다.

| 규칙 | 조건 | 적용 여부 |
|---|---|---|
| `MORNING_RUSH_MERGE` 정체·차선 변경·합류·끼어들기 | 출근 피크 | 적용 |
| `LUNCH_SHORT_TRIPS` 단거리 이동·주정차·보행자 | 점심 피크 | 적용 |
| `EVENING_RUSH_CUTIN` 정체·Cut-in 가능성·복잡한 합류 | 퇴근 피크 | 적용 |
| `SUNRISE_LOW_SUN` 저각도 역광·노출 변화 | 일출 전후 | 적용 |
| `SUNSET_GLARE` 역광·급격한 조도 변화 | 일몰 전후 | 적용 |
| `NIGHT_LOW_LIGHT` 저조도·헤드라이트 Glare·인식 거리 감소 | 조도 야간 | 적용 |
| `RAIN_REFLECTION` 노면 반사·차선 가시성 저하·물보라 | 기록에 있는 우천 날씨 | 적용 |
| `SCHOOL_ZONE_ARRIVAL` / `APARTMENT_ADJACENT` / `INTERSECTION` | 어린이보호구역 · 아파트 인접 · 교차로 | **미적용**(해당 데이터 없음) |

차량속도(평균·정차·저속 비율)는 "참고 관찰"로만 적고 정체로 단정하지 않습니다(실제 데이터의 31%가 0km/h = 정차·대기 포함).

### 추천 탭 사용법

맨 위 **오늘 추천 주행**만 보면 바로 나갈 수 있게 했습니다. 기존 분석 화면(아래 1~7 · 자동 분석 · 세부 구역 · 주행 계획)은
**상세 분석 보기**를 누르면 펼쳐집니다(접은 상태는 기억합니다 · 접어도 계산·캐시는 그대로).

**오늘 추천 주행 — Top 3** (`Recommendation.buildTodayPicks`, 새 점수를 만들지 않고 이미 계산된 추천에서 고름)

```text
오늘 추천 주행   2026-09-30 (평일) · 09:00 ~ 18:00 · 차량 1대 · 적용 정책: 2026-10 우선 수집 요청
① 논현로94길 · 논현로 → 언주로93길          강남 ⑩구역 · 교차로 밀집 구간      ← 어디
   평일 17:00~17:45 · 약 45분 · 양방향                                      ← 언제
   퇴근 피크 데이터 부족 + Coverage 부족                                     ← 왜(데이터 부족)
   사업 우선 구축지역 ⑩                                                     ← 왜(활성 정책, 우선도 0이면 안 나옴)
   [지도] [근거] [숨기기] [완료]
```

- 오늘(한국 날짜)의 요일 유형(평일/주말)과 운행 시간(주행 계획과 같은 입력)에 겹치는 도로 구간 추천만 고르고,
  숨김·기간 제외·완료 상태를 적용한 뒤 **같은 구간은 한 번만** 점수 순 3개 → 시간 순으로 보여줍니다.
- **구간 이름**: 구간 양끝에서 만나는 다른 도로 이름(HD Map 에 실제로 있는 이름)으로 `도로명 · A → B`(진행 방향 기준),
  없으면 `도로명 · 구간 #N`(도로별 서→동 순서의 짧은 번호 — 다시 분석해도 같음). 그래도 겹치면 구간 번호로 바꿔 구분합니다.
  IC·역 이름은 HD Map 에 없어 만들지 않습니다. 내부 segmentId 는 카드 **근거**의 "구간 ID"에서만 보입니다.
- 도로 구간 분석이 아직 없으면 구역 추천으로 대신하고 그 사실을 적습니다. 여기서 숨기거나 완료한 구간 추천은
  같은 영역의 "숨김·완료한 도로 구간 추천"에서 되돌리고, 완료·제외할 때 **그때 적용된 사업 우선 정책**도 함께 저장합니다.

**상세 분석**

1. **추천 요약** — 기준일·데이터 범위·후보 수·우선순위 분포·KPI/제안 목표 대비 부족량
2. **필터·정렬** — 구역 / 평일·주말 / 교통 시간대 / 조도 / 날씨 / 차량 / 최소 신뢰도, 정렬은 추천 점수·Coverage 낮은 순·
   수집 시간 부족 순·마지막 방문 오래된 순(기본: 추천 점수)
3. **추천 카드** — 순위·구역·조건 배지·권장 요일/시간·현재 수집 대 목표·부족한 수집 시간·현재 방문 대 목표·권장 추가 횟수·
   현재 Coverage·미방문 Cell·마지막 방문·부족한 조건·예상 확보 조건·추천 점수·우선순위·신뢰도·추천 이유
4. **근거 보기** — 항목별 현재 상태·점수·가중치·적용 가중치·반영 점수 표(합이 최종 점수와 맞아 검산 가능), 목표·비교 기준,
   권장 시간 계산 근거, 적용/미적용 Edge Case 규칙, 데이터 범위·누락·신뢰도 이유, LLM 전달용 JSON
5. **현재 데이터 부족 현황** — 구역별(수집·방문·수집일·마지막 방문·Coverage), 교통 시간대별 목표 대비, 평일/주말·조도·날씨·차량 분포
6. **추천 설정**, 7. **데이터 한계·신뢰도 안내**

카드 버튼: `이번에는 숨기기`(저장하지 않음) · `N일간 제외` · `수집 완료로 표시` · 숨김 목록에서 `다시 추천받기`.
**수집 완료로 표시해도 주행 기록은 바뀌지 않습니다.** 그때의 실제 수집량을 함께 저장해 두고, 새 데이터가 들어오면
목표를 채웠는지 비교해서 채웠으면 계속 숨기고, 아직 모자라면 "다시 추천"으로 되살립니다.

### 추천 설정

가중치 6개 · 교통 시간대별 목표 수집 시간/방문 횟수 · 기본/구역별 목표 Coverage · 최소 고유 수집일 · 오래된 방문 기준 일수 ·
추천당 최대 권장 횟수 · 추천 결과 개수 · 기간 제외 일수 · 낮은 신뢰도 표시 여부. `기본값 복원` 버튼이 있고, **가중치 합계가
100%가 아니거나 값이 범위를 벗어나면 저장하지 않고 이유를 표시**합니다(저장소도 같은 검증을 다시 합니다).
설정을 바꿔도 원본 주행 기록은 바뀌지 않습니다. 목표 기본값(피크 240분·4회 등)은 데이터에서 나온 값이 아니라 첫 버전의
정책값이라, 운영 목표에 맞게 바꿔 쓰는 것을 전제로 합니다.

### 캐시와 자동 갱신

추천 캐시 키에는 `데이터 · 구역 · 수동 Coverage 셀 · Coverage 스냅샷 · 시간 분류 기준 · 추천 설정(도로 구간 추천 설정 ·
사업 우선 정책 포함) · HD Map 우선 구역 경계` revision 과 차량 필터,
오늘 날짜(한국 기준)가 들어갑니다. revision 은 저장소 변경 알림으로만 올라가서, **탭을 오가기만 하면 DB 조회도 재계산도
하지 않습니다.** 다시 계산하는 경우: Import · 삭제 · 백업 복원 · 서버 동기화 · 구역/경계 변경 · 수동 방문·미방문 셀 변경 ·
Coverage 재계산 · 시간대/조도 설정 변경 · 재분류 · 추천 설정 변경 · 날짜가 바뀐 경우. 필터·정렬·숨김/완료 처리는 다시 계산하지
않고 목록만 바꿉니다. 늦게 끝난 예전 계산은 최신 결과를 덮지 않습니다.

Coverage 스냅샷은 누적 지도에서 "커버리지 갭 보기"로 계산할 때 저장됩니다(전체 기간 계산만). 저장할 때 데이터·경계·수동 셀
지문을 함께 적어 두고, 그 뒤 무엇이든 바뀌면 "오래됨"으로 보고 **Coverage 항목을 점수에서 빼고 신뢰도를 낮춥니다**.

### 주행 계획으로 이어보기

추천 카드는 "무엇이 부족한가"까지입니다. 그걸 **오늘 몇 시부터 어디로** 로 바꾸려면 같은 탭 위쪽의
[주행 계획](./drive-plan.md#주행-계획--그-시간에-나가면-어디부터-어떻게-돌까)을 쓰세요 — 같은 점수 규칙을 그대로 써서
운행 시간을 블록으로 나눠 배치합니다.

### 향후 확장

- **실제 Edge Case 로그**: 추천 데이터 모델에 `observedEdgeCases`(지금은 항상 빈 배열) · `predictedEdgeCaseHints` ·
  `edgeCaseEvidenceLevel`(지금은 `condition_only`)이 이미 있습니다. 검출 수·급정거·TTC·Cut-in·불법 주정차·공사 구간·
  신호/차선 인식 실패·센서 이상·수동 개입 로그가 들어오면 `observedEdgeCases` 를 채우고 근거 수준을 올리는 방향으로 넓힐 수 있습니다.
- **LLM 연결**: `Recommendation.toLlmPayload(추천)` 과 `buildLlmContext(결과, 추천들)` 이 구조화된 사실만 만듭니다.
  원본 GPS 좌표·사람 이름·차량 이름은 넣지 않습니다(테스트로 확인). LLM 은 이 결과를 설명·비교·질의응답에만 쓰고,
  순위·수치·Edge Case 를 새로 만들지 않도록 지시문을 함께 넘깁니다.
